# Collie Writer purchase service

This is an unpublished production integration, not a testing harness. **Local source checkpoint only.** Checkout is disabled in `policy.mjs`; the desktop origin is null and issuer keys are empty. [D7](../../docs/decisions/D7-direct-commerce.md), the [wire/storage contract](../../docs/formats/direct-commerce-v1.md), and the [prerequisite register](../../docs/commerce/stage-20-prerequisites.md) govern enabling it. The assistant has not started this service, created keys/accounts, sent webhooks or made a purchase.

## Owner setup after the prerequisites are resolved

1. Record the commercial-value decision. Complete actual seller/Paddle eligibility and sandbox setup using the owner's identity. Create active USD prices: 999 cents per month and 19900 cents one-time, quantity one, no trial and no country price overrides. Both are the nonfiction edition. Configure the United States launch market with the provider; the local adapter does not restrict checkout geography.
2. Supply an approved HTTPS domain and a private Linux service host with Node 24.21.0. The service uses built-in `node:sqlite`; runtime refuses SQLite below 3.51.3. Do not share the database over a network filesystem or run multiple service replicas. No npm install is needed for this dependency-free service.
3. Provision the genuine Ed25519 private key through the operator's key-management process. Set a distinct issuer and key ID per sandbox/live environment. Private keys never enter Git or desktop assets. Put the key in a private absolute file (0600), and the database under a pre-created private directory (0700). Populate the variables named in `.env.example` using the host secret manager. It supplies no fake identity, price ID, domain or key. The service does not automatically load a repository `.env` file.
4. Configure a TLS reverse proxy that forwards the canonical Host, rejects other hosts and limits request size/rate. The Node listener binds only `127.0.0.1`; the public URL is HTTPS. Preserve exact webhook request bytes. Do not log Authorization headers, bodies, recovery codes, URL fragments, provider portal query strings or full API responses. Keep host clock synchronization healthy for five-second signature tolerance. The built-in bounded queue/global rate cap is a backstop; perimeter abuse protection is still required.
5. Register the Paddle notification URL `/webhooks/paddle`, selecting transaction, subscription and adjustment lifecycle events. Store the destination's authentic webhook secret separately. The handler keeps a minimal durable receipt and returns before canonical processing; pending rows retry with backoff. Repeated event IDs cannot repeat fulfillment. Explicit desktop refresh reconciles current provider records if a notification is missed.
6. Add the actual public SPKI key to desktop `keys.ts`, set the matching service origin/environment/issuer in `direct/config.ts`, and use isolated sandbox build/data identity. Keep sandbox trust anchors out of live builds. The service also prevents reuse of a signing key ID with different bytes.
7. Review the drafted pages, seller/support values, allowed geography, public Paddle client configuration, provider surface/network behavior and permanent no-ads requirement. Provider-required additional CSP origins require explicit review; do not replace the deny-by-default policy with `https:` or `*`. Once the product decision and provider review are recorded, change `policy.mjs` and the desktop `checkoutApproved` setting together. These flags do not themselves authorize deployment or purchases.
8. After separate hosting authorization, the operator starts the service with its configured environment using `npm --prefix services/entitlements start` from the repository root, or `node server.mjs` from this directory under a supervised process. These are operator launch instructions, not commands the assistant executes. Actual sandbox transactions are user-operated and require their own authorization. Follow the [manual guide](../../docs/manual-testing/stage-20.md); never substitute simulated grants or success redirects for evidence.

## Operation and recovery

- The desktop contacts the service only on explicit purchase/restore/check/refresh/manage/disconnect actions. Have subscribers refresh online to receive renewal/revocation state before signed grace ends. A service outage does not erase cached grants or affect project recovery/export. This service has no content-upload route.
- Keep the checkout browser page open long enough to save the purchase recovery code to a password manager. Restore on a replacement Mac or Windows machine starts in that app, enters the code in its system browser, and finishes back in that app. Each connection uses independent random credentials. No device fingerprint or project limit is introduced.
- A lost code requires verification of ownership in the merchant record. Stop the service for a support database operation. In a private terminal with recording disabled and the same configured environment, an authorized operator can run `node support-recovery.mjs replace-code <verified-customer-id> --ownership-confirmed`. It reconciles actual merchant purchases and emits a fresh recovery code **only after commit**. Deliver that code through the owner's established secure support channel; never ask for manuscript data. This does not mint a payment or synthesize a signed grant.
- For lost-device connection cleanup, the authorized operator uses `node support-recovery.mjs disconnect-devices <verified-customer-id> --ownership-confirmed` while the service is stopped. It revokes service connections and pending browser sessions. Cached offline licenses cannot be remotely erased by this action. This is separate from refund/revocation of purchase rights.
- Failed transaction creation can leave an unpaid merchant draft with an unknown local outcome. The adapter does not secretly retry a purchase. Start a new session only through a user action; use the real receipt/support process if a payment was actually completed but the browser session expired before the recovery code was retained.
- Do not change configured price IDs while outstanding purchases still use them. The initial contract supports the two approved prices only. Catalog changes require an explicit historical-price mapping migration; otherwise reconciliation stops rather than silently revoking old buyers.
- Monitor pending-event age, attempts and generic service error counts without storing payloads. Externally reported failures or provider response changes require source fixes and another user-owned manual guide. No assistant-run probes, simulator, scripts or automated checks are part of this workflow.

## Backup, migration and key rotation

Purchase records are non-content metadata but are still private. Before a service/schema change, stop the sole writer cleanly and retain the whole database and any WAL/SHM files together in restricted backup storage, or use a vetted SQLite online-backup facility operated by the owner. Never copy an active main database alone. Store signing-key backups separately under the operator's access controls. No automatic service migration is implemented: only an empty database initializes to schema 1; unknown schemas are refused and retained.

Revision counters and revoked records must not move backward during disaster recovery. Keep the durable current ledger/continuous backup. Do not restart signing against an older backup as though it were current: clients reject old revisions, and unseen revocations could be lost. If the current revision high-water marks cannot be recovered, keep issuance off and plan explicit reconciliation/recovery before resuming. No new key ID or issuer is a shortcut around lost anti-replay state.

For planned signing rotation, provision a new real key under a new key ID, ship its public key alongside prior valid keys, and then switch service signing. Reconciliation advances the purchase revision under the new key. Do not delete old public keys merely because the active key changes. A compromised key requires a separately reviewed incident/client-update plan; an indefinitely offline client cannot learn a trust-anchor change immediately.

Desktop unreadable access caches remain preserved by Stage 18 and require support; this stage does not silently discard their replay ledger. Disconnect only clears bearer connection state. Public pages and operational copy are drafts until the owner approves actual seller/retention/refund/support arrangements. No uptime, native behavior, compliance certification, provider approval or successful purchase is claimed.
