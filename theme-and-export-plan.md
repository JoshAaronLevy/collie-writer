# Collie Writer theme and export implementation plan

## Status, purpose and relationship to other plans

**October 2, 2026 — planning only, awaiting Josh's review. No TE stage is implemented or authorized by this document.** At Josh's request, this plan takes ownership of the four publication stages previously called I12A, I12B, I12C and I12D in [app-improvement-plan.md](app-improvement-plan.md). Their detailed scope and design direction are preserved here as **TE01–TE04**. The app improvement plan retains I01–I15 and a cross-reference; it no longer duplicates these stage briefs or requires their completion for I15.

The feature should let a nonfiction writer give a paper, report or book a considered professional appearance, see that treatment on a small portion of their own writing, and export the intended contents without a complicated publishing setup. A curated theme pairs body text with chapter titles, numbering and other document roles; it is more useful than an overwhelming list of unrelated fonts. The goal is broad print and e-reader compatibility with clear format-specific behavior, not decorative typography or identical pagination everywhere.

This plan extends the existing local Export workspace and compilation pipeline. It does not replace the manuscript editor, change the app's light/dark theme, or require AI. It was originally placed after I12 in the improvement sequence; as a separate plan it can be explicitly requested when its local prerequisites are delivered, without waiting for conversations, proofreading, provider activation or I15. It does not authorize implementing those other plans, and earlier completed stages need no rerun.

[AGENTS.md](AGENTS.md) remains authoritative for semantic CSS, data safety and user-owned manual testing. The [MVP plan](mvp-implementation-plan.md) owns established product/storage/access contracts; the [app improvement plan](app-improvement-plan.md) owns the Mantine experience and persistent workspace. The [conversation](conversation-implementation-plan.md) and [proofreading](proofreading-implementation-plan.md) plans are independent. Changes from whichever plan runs first must be respected when allocating versions and extending shared owners.

## Product experience and boundaries

The Export workspace should lead through **Contents → Theme & layout → Preview → Export**, with the current selections visible and advanced settings collapsed. This is one coherent workspace, not another onboarding flow or a new permanent column beside writing. Reuse I09's scope, issues, recipes, native destination selection and persistent job results.

- **Contents to export:** whole active manuscript by default for a new export session, or explicitly chosen chapters/text sections in manuscript order. Exclude archived/trash content. Existing saved recipes keep their exact saved selection. Show the output scope and section count near the final Export button.
- **Preview sample:** independently choose the opening, current text section, or a selected chapter/section. Default to a short opening sample; a chapter can itself be sampled if long. Previewing a small part must not narrow export contents. A user may deliberately export an excerpt through the separate Contents control.
- **Theme:** present an accessible gallery with actual bundled-font samples for a chapter heading, number and paragraph. Give each theme a short practical description. Filter by Book, Academic or Report if helpful, with all choices still available for every nonfiction project type. No script, decorative novelty or handwriting fonts. Interface light/dark appearance and editor typography remain separate from publication styling.
- **Layout:** start with a useful preset and reveal a small number of meaningful controls: paper/trim size for print, body size/leading within readable bounds, paragraph treatment and chapter numbering. Keep citation style independent. Neither an “Academic” theme nor APA/Chicago citation formatting claims compliance with a particular journal's entire submission specification.
- **Output:** offer PDF for page-based reading/printing, DOCX for editable handoff, EPUB for reflowable e-books, and existing Markdown/plain text for interchange. Explain format differences beside the choice. Preserve existing metadata warnings and captured-revision acknowledgment; add only actionable font/layout/format issues. Export never changes the project's selected `.collie` save location.

**Starting theme collection:** aim for these ten coordinated themes, using four restrained font families rather than a long font dropdown. Names and spacing may be refined from Josh's visual feedback; the variation in hierarchy and reading feel is required. Source Serif 4 is already bundled. Additional families below are candidates to pin with appropriate static faces and redistribution/embedding evidence in TE01.

## Compatibility contract

“Compatible with printing or e-readers” means standards-based output with a documented target matrix and readable fallbacks. A font/theme alone cannot guarantee acceptance by every printer, store or reading app. These are separate rendering contracts:

| Format                | Theme behavior and intended use                                                                                                                                                                | Honest limitation                                                                                                                                        |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PDF                   | Frozen page geometry and typography, licensed embedded fonts, print-oriented black text on paper.                                                                                              | A book interior still needs the target printer's trim, margins and production requirements. No blanket PDF/X, cover, bleed or press-ready certification. |
| DOCX                  | Real document styles, editable text, headings and native notes, appropriate licensed font embedding/fallbacks.                                                                                 | Word processors can substitute fonts or repaginate. The app's paginated preview describes its PDF layout, not every word processor's rendering.          |
| EPUB 3                | Reflowable structure and a matching theme treatment, usable navigation, reader-controlled sizing and body-font defaults. Offer publisher typography as an optional preference where supported. | Reading software may ignore or override fonts/layout; fixed print page counts and footnote placement do not carry over.                                  |
| Markdown / plain text | Preserve existing semantic/text export and honest loss reports.                                                                                                                                | These formats do not preserve a coordinated page/font theme.                                                                                             |

Primary documentation reviewed for this planning addition: [W3C EPUB 3.3](https://www.w3.org/TR/epub-33/) defines the portable publication format; [EPUB reading systems](https://www.w3.org/TR/epub-rs-33/) describes reading-system behavior. [Kindle's reflowable text guidance](https://kdp.amazon.com/en_US/help/topic/GH4DRT75GWWAGBTU) supports reader control over body text and optional publisher fonts. [KDP's content routes](https://kdp.amazon.com/en_US/help/topic/G79CTKR8BX79E96L), [Apple Books preparation](https://itunespartner.apple.com/books/support/9-prepare-book) and [Kobo's accepted file types](https://kobowritinglife.zendesk.com/hc/en-us/articles/360059386271-File-Types-Sizes) support EPUB as a distribution input. Kindle submission/conversion is distinct from a claim that every Kindle directly opens `.epub` files. Print guidance requires attention to [embedded fonts](https://kdp.amazon.com/en_US/help/topic/G202145450) and [manuscript-file preparation](https://kdp.amazon.com/en_US/help/topic/G202145060); [print options](https://kdp.amazon.com/en_US/help/topic/G201834180) are target-specific. Refresh relevant official requirements during implementation; observed output remains user-owned acceptance. No publishing account, upload, store submission or paid conversion service is authorized by these stages.

## Shared implementation contracts

These apply to every TE stage even when the user requests only its ID.

1. **One local workflow and clear ownership.** Reuse the existing persistent workspace/session, draft registry and export jobs. Protect pending writing/source/note/details changes before capturing output through the existing choices. Navigating to another view or project cannot redirect a job, discard a draft or alter a frozen output. Local recovery, project-file Save and publication export remain distinct operations.
2. **Semantic styling and accessibility.** Use Mantine and the existing theme APIs. Author descriptive lowercase hyphenated classes in the smallest component/feature/shared owner, such as `publication-theme-card` or `publication-preview-container`. Prefer semantic CSS Modules; no utility stacks, generated-hash targeting or feature CSS dumped into the root stylesheet. Keep keyboard operation, focus return, high contrast, reduced motion, narrow layouts and 200% zoom in scope. Print pages remain paper-like while surrounding controls follow app appearance.
3. **Separate manuscript, settings and output.** Typography and generated chapter numbering are publication decisions, not editor AST mutations. Keep human titles, intentional inline formatting, citations, managed images, tables and native notes intact. Theme/citation styles and preview/output selection are distinct choices. A theme change cannot silently change which chapters will be exported or create manuscript content.
4. **Immutable capture and bounded work.** Freeze content, title/byline, selected source/style revisions, publication settings and required assets at one authoritative boundary. Preview and final-export digests identify their respective exact scope. A sample is not approval of unseen full-output issues. Limit decoded content/assets and concurrency before costly processing, provide cancellation and stale/error states, and never solve sample performance by compiling the full book then hiding pages.
5. **Formats, migrations and copies.** TE01 owns the next needed frozen compilation version; TE03 owns persisted format-vocabulary safety for EPUB; TE04 owns enhanced portable recipes/layout. For every persistent extension update strict shared/main/preload/worker validation, schema and retained-copy migrations, portable database/manifest/archive readers, snapshot/Open/Save, Backup, Duplicate/Restore and rekey/reference handling together. Preserve supported old reads, originals and failed candidates. Use actual delivered versions from other plans; neither reserve numbers nor edit earlier stages to pretend the new format already exists.
6. **Portable versus device-local.** Saved recipes contain stable selected section IDs, versioned theme/layout and relevant per-format preferences. They travel with project files and copies. Temporary preview samples/bytes, active jobs, native destination grants, local filesystem paths and caches do not. Preview cleanup must never delete retained exports, recovery candidates, project assets or backups. Exact operation IDs, revisions and unknown-result retries remain required for recipe writes.
7. **Access, privacy and file safety.** Ad-hoc preview/theme selection and single-format export remain available for readable projects, including read-only projects. Preserve paid named-recipe creation/editing and multi-format batch boundaries; no new typography paywall or promotional upsells. Use native destinations and existing overwrite/collision/cancellation safeguards, retaining completed outputs. No AI login, remote font/content hosting, content diagnostics, ads, publishing accounts or automatic upload.
8. **Trusted rendering and licensed resources.** Font families/faces, CSS and resource paths come from a validated local registry and captured manifest. Preserve renderer sandboxing, context isolation, narrow IPC and deny-by-default networking. The existing isolated print-session exception does not authorize broader app CSP changes. Keep font licenses, citeproc attribution/source and style/locale notices; a selected font name alone is not proof of embedding rights or glyph coverage. Preserve current page-footnote/output fidelity gates.
9. **Truthful compatibility and acceptance.** Treat the primary references above as design inputs and refresh relevant requirements during the requested implementation stage. Code delivery is separate from user-observed font embedding, reader behavior, printing, native destinations, large-project performance and accessibility. Do not promise universal acceptance or close the independent release NO-GO from source inspection.
