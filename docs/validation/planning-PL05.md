## Proposal production and presentation

- `shared/outline-proposals.ts` defines exact proposal v1 output, input, version and command/result contracts. Titles, purposes, kinds, references, duplicate assignments/positions, parent cycles/depth and bounds are checked. Existing chapter IDs must come from the captured outline metadata. Material IDs must belong to original ranges actually covered by the producing analysis, independent of mounted board pages. Unknown IDs or malformed output invalidate the entire proposed result; its original conversation output remains readable.
- `planning-conversation.ts` retains additive analysis v2 and nested planning payload v2 inside the existing capture v7/review v8. It freezes outline metadata, relevant canonical links, sibling-order hashes and the exact saved version selected for refinement. Chapter scope bounds editable existing documents to that branch and its ancestors within the supplied overview. Other scopes use the existing bounded, exclusion-aware overview. No manuscript bodies or live execution authority enter these records. PL04 summaries, coverage, invalidation, explicit Continue and request budgets remain their existing owners.
- `main/ai/content-service.ts` appends the frozen proposal v1 format instructions to the actual request consistently during review sizing, dispatch and reconciliation. The visible chat message remains the user's prompt, and sent context includes the schema and original input. Existing own-account text/research templates and operation versions remain; no provider route, key, proxy, model-selection or commercial-approval change is introduced.
- Completed valid output is retained as the first immutable proposal version inside the existing conversation settlement transaction. Invalid or over-limit output remains protected text with a concrete review issue. No generated result changes the live outline, and there is no automatic repair request.
- `PlanningChatControls`, `conversationState`, `ResearchAnswer`, `PlanWorkspace`, navigation and `OutlineProposalPanel` connect **Create editable outline → Send → Review outline**. Cards expose title, purpose, parent, sibling position, added/removed material and gaps. Earlier/later buttons and labeled fields support keyboard use. Twenty cards are mounted per page; material selectors limit visible search choices. Editorial suggestions start unchecked. Original output remains under a contextual disclosure.
- The proposal editor is retained in Plan, with one draft registration and exact pending operation. Save edits creates a new immutable version; Dismiss and guarded navigation also protect changed derivative content without applying it. Keep discussing saves the chosen version and prepares the shared chat draft, preserving existing unsent text. Send is still explicit. Replies create separate proposals; they never replace an edited version. The existing draft file adds version 3 for the optional nested planning v2 outline/refinement choice; older file contracts stay exact.

## Atomic application, conflicts and recovery

`worker/projects/outline-proposals.ts` runs through the existing serialized repository, capability checks, main/preload validation and file-operation boundary. Apply uses one SQLite transaction and a stable operation ID/request digest. It checks the current head, captured chapter revisions/active ancestry, affected sibling membership/order, analyzed material ranges/revisions/exclusions and targeted link before-values. Newer work produces a specific refusal; the proposal remains available for editing or explicit discussion. No inference is sent to resolve a conflict.

The operation creates real empty chapters/sections, changes only displayed title/purpose/parent/order, preserves unspecified chapters and all current manuscript payloads, and applies canonical association changes plus explicitly selected dispositions. Unspecified links and Research verification decisions remain. The existing manuscript checkpoint, anchor reconciliation, material revision/history and disposition owners participate in the same transaction. No independent create/move/link call sequence or second live outline is introduced.

Apply records generated document IDs and bounded structural/link/disposition before/after values. Existing `domain_operations` retain exact commit receipts. Repeated requests return the original receipt. A lost acknowledgment stays pending in the retained editor; **Check change**, Save and navigation reconcile through a read-only status call. They do not repeat a mutation. The existing manuscript owner adopts a confirmed outline while retaining an unchanged editor payload and Undo state. A response can be applied only once across all of its edited versions, preventing new chapters from being duplicated by another version selection. Revision after application requires an explicit fresh proposal through Keep discussing.

**Undo outline change** checks only its recorded structural fields, affected sibling groups, targeted links and changed dispositions. Existing-document payloads and later status/prose remain current. New chapters must still be unchanged and empty, without newer children or unrelated links; otherwise the complete inverse is refused. An inverse retains empty created chapters in Trash and restores original active ordering/associations/dispositions. It does not physically delete records or use whole-manuscript History restore as an assignment undo. Both apply and inverse add ordinary structural checkpoints. A later manual History restore can make an old inverse unsafe; the retained apply record is not erased or automatically replayed.

Source review also corrected stationary proposed positions during insertion, input-limit reporting being masked by a follow-up read, the placement of output-format instructions, read-only access to older proposal versions, and inactive Plan dialog presentation. These are source findings, not observed runtime results.

## Migration and portability

SQL/minimum reader **43** adds `outline_proposal_versions`, its attempt index and `outline_proposal_applications`. Schema-42 DDL stays frozen. The retained-copy 42→43 migration validates existing schema/conversations before adding empty storage. `manifest.ts`, exact shared/worker validators, `incoming.ts` and portable conversation admission are updated together.

Admission validates version ancestry/limits, exact original AI output, captured eligible references, retained baseline proposal identity, inverse shape and its relationship to the applied version, document ownership and apply/undo receipts. Frozen analysis inputs include stable content/document IDs and order hashes, without embedded project/workspace authority. Independent copy remaps outer project IDs and uses existing commit-receipt remapping. Save, Backup/Restore, retention and migration use their existing database owners. Credentials, local drafts and live bindings remain device-local. Earlier analyses, captures, history, note/source identities, originals and recovery records are retained.

Bounds: at most 100 proposed changes and 100 dispositions; 100 references per chapter and 1,000 total add/remove references; title 500 units, purpose 2,000, ten gaps of 1,000 each; complete proposal JSON at most 128,000 units. Input metadata and earlier proposal are bounded to 30,000 units, 200 supplied outline items, 2,000 association rows and 401 sibling hashes. The original planning overview can be partial; the review shows how many existing outline items were supplied and leaves others intact. Large input asks for a chapter scope, fewer linked items or a shorter earlier proposal. There are at most 100 retained versions per producing response and 10,000 per project; inverses are bounded to 16 MiB. Existing PL04 analysis/request/output and manuscript/link limits still apply. Limits refuse without truncating a proposal or partially writing an outline. A very large edited proposal can remain locally useful even when it is too large to send back for refinement.
