## Implementation and ownership

- `app/navigation.ts`, workspace navigation/views and `WorkspaceModeSwitch.tsx` add **Plan** inside the existing retained project session. Write remains the project-opening destination. `useWorkspaceController.ts` keeps Plan visible after its outline operations and reopens the existing writing document for adoption, preserving the mounted editor/Undo when its content is unchanged. It retains the exact outline operation until the new state is adopted. Plan forms participate in existing draft guards; only their submitting action excludes its own draft during preflight.
- `features/planning/PlanWorkspace.tsx`, `PlanningCards.tsx` and the scoped stylesheet provide the Material rail, outline grid, optional topics, material details, selection/actions and a responsive single-pane switch. They use Mantine, Tabler and semantic scoped CSS. The material pool, linked contents, topic/chapter grids and detail association lists render 20 entries per page. No source file or full conversation is mounted as a card. Title/type/development filters run over the complete requested scope. Original surfaces remain retained, including unsent chat drafts.
- `usePlanningPreferences.ts` stores bounded device-local hints for the last project: filter/query/type/status, selected group/outline level, pane, pages and scroll. These never authorize edits or travel inside `.collie`. `usePlanningPage.ts` rejects late results for another request/scope and keeps the same page’s cards mounted during refresh; stale/loading reads disable edits.
- `shared/planning.ts` defines exact project-scoped readers/edits and sparse metadata. `worker/projects/planning.ts` owns full-scope filtering, counts, bounded visible-page projection and atomic batch changes. Canonical note/source/chat/excerpt associations remain under the existing material-link authority and retain revision guards. `material-reader.ts` extracts the existing bounded metadata/preview reader for both Plan and Chapter material. Previews are at most 400 characters: note text, source bibliographic details, exact excerpt text or an available native user message. Imported chat cards retain their title/origin and open the complete transcript through its existing reader; no bounded AI recall is presented as the full original.
- Topics are ordered, one-level reference groups. Material can be in multiple groups/chapters. Pool dragging adds references; dragging direct chapter/topic assignments moves only the indicated source membership. Add to, Also use in, Move to, Remove, and earlier/later controls provide keyboard alternatives. Chapter dragging reorders siblings in the real outline; parts and nested sections use focused expansion/breadcrumbs. Outcomes name the destination and restore focus to the affected card/group.
- **Make chapter** calls the existing outline create operation inside the planning transaction, unions all topic references into the new empty document and removes only the converted topic/memberships. Other memberships, editorial dispositions and original bodies remain. A failure rolls back the entire operation. Manual chapter creation/title/purpose/order uses the existing outline operations. New chapters/sections are empty; no generated prose is inserted.
- Keep is the implicit default. Needs development stores an optional reason; Set aside preserves originals, chapter/topic links, citation occurrences and Research decisions. The ordinary pool excludes it; Set aside and selected-group disclosure recover it. `ChapterMaterialPanel.tsx` uses the same planning read projection and shows set-aside links in a separate expandable group. Restore to Keep restores ordinary planning availability.
- Shared project commands, main/preload IPC, capability classification, worker dispatch/repository carry the new read/change operations through existing project ownership and editing rights. Changes use an exact operation ID/digest, expected head and retained ordinary commit receipt. Check change/Save/navigation reconcile uncertain planning outcomes with a read-only status call; they do not repeat a planning mutation automatically. Draft dialogs retain Save/Cancel and pending recovery. Read-only access retains inspection/original navigation.
- The Plan header’s **Import material** opens the existing import dialog. **Add note** sends a one-time intent to the retained Notes owner, which creates/edits the ordinary note and does not repeat the intent on Back. PL03 still owns file drop, paste/source capture, passage origins and the integrated import follow-up. Plan has no new AI composer, provider route or automatic request.

## Migration, history and portability

SQL/minimum reader **40** adds `planning_topics`, `planning_topic_members` and `planning_dispositions`; schema-39 DDL/readers stay frozen. The retained-copy 39→40 migration validates the source and adds empty planning metadata, requiring no reimport/enrollment. Earlier chat-origin seeding remains a one-time schema-39 migration.

`manifest.ts`, `portable-db.ts`, `incoming.ts`, schema/migration owners and exact shared validators are updated together. Portable admission validates ownership, bounded counts, exact metadata, unique positions/memberships, material existence and history records. Independent copy remaps outer project IDs on all three new tables; embedded snapshots contain material/document/topic identities without project/workspace authority. Save, Backup/Restore and retention hashes already include all admitted tables. No originals or recovery records are treated as cache.

New `chapter_material_history` bodies use **v2**, retaining links plus topic/membership/disposition snapshots. The manuscript snapshot format stays unchanged. Existing history byte accounting/pruning includes these bodies. `HistoryPanel.tsx` explains the expanded restoration scope.

| Saved version | Restoration                                                                                                                                                 |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| New v2        | Restore writing/outline, saved links and Plan metadata; retain current writing/Plan in the pre-restore version. Research bodies/states are not rolled back. |
| PL01 v1       | Restore captured links, preserving current topics and editorial metadata.                                                                                   |
| Pre-39        | Preserve current links and Plan metadata because the old version captured neither.                                                                          |

Existing merge/split/archive identity rules remain. Converting a topic keeps its before-state in the structural checkpoint, so restoring that version can recover the topic and links. A whole-manuscript restore remains an explicit History action, not the normal inverse of one assignment.

Limits: 1,000 topics; 200,000 memberships and 200,000 non-default dispositions; batches of 100 selected items; metadata JSON below 32 MiB with a 1 KiB history margin; v2 history bodies at most 64 MiB, with PL01 v1’s 32 MiB limit retained. Outline/link limits remain their existing contracts. Limits refuse the transaction without truncation.
