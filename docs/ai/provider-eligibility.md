Write documented code paths before account access is available. Keep unknown inputs unset and refuse dependent live actions; do not simulate successful sessions or invent auth/funding methods. Login can be available while inference is blocked where the route permits it. The following steps describe actual runtime responsibilities, not prerequisites forbidding code development.

1. Map the documented technical route, applicable terms, supported platforms, required auth configuration and branding. Write supported code with missing registration/access inputs unset; record actual approval/registration when supplied before enabling its dependent actions. 2. Main owns the sign-in attempt, approved browser destination, callback listener/transport, and validated result. For the documented local flow, state, nonce, PKCE, exact loopback redirect, ID-token validation, granted scopes, issued client identity, and stable host identity are distinct requirements. Keep them separate from renderer state. The commercial route must explicitly establish which contract applies. [Registration and sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in).
3. Store each validated account/client registration separately in protected device-local storage. [Accounts and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions).
4. Start an isolated child with only the approved configuration and short-lived credential transport. [Adapter](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server).
5. Refresh before a request when needed. The documented environment-token configuration requires app-server restart to pick up a renewed token. Resume only if retained context still matches the user's selected scope. ## Funding semantics and the unresolved control

**Required by Collie:** for every submitted operation and each internal continuation/model/tool request, the provider enforces that only the user's included subscription allowance can fund it. At exhaustion, the request must stop/refuse without using purchased credits, shared paid balances, top-ups, or API-key billing. This must hold during concurrent usage and account-setting changes, not merely at a balance preflight.

OpenAI documents a user control permitting other apps to use credits after plan limits. That is relevant evidence of a funding choice, but these pages do not establish how Collie can bind and authoritatively enforce the disabled-credit state for the complete operation. Do not substitute a checkbox in Collie, a screenshot of provider settings, or a zero balance observation for the required guarantee. [Provider usage controls](https://learn.chatgpt.com/docs/sign-in-with-chatgpt).

Acceptable future evidence could be an official included-only request capability or a provider-enforced client/account policy whose scope, readability, change semantics, and handling of internal calls establish the same guarantee. Record its exact supported field/policy and response semantics when supplied. **No such field is invented here.** A dollars/tokens budget is not automatically an included-only funding selector. Stop/cancel cannot undo already consumed allowance or prove that no credits were charged.

For Grok, existing credits being used after the weekly allowance is exhausted makes no-API-key authentication insufficient. For Claude, the paused credit announcement must not be used either as current metered-only policy or as proof of included-only commercial rights. Each adapter requires its own evidence; approval of OpenAI does not carry across providers.

Use an app-owned runtime directory/profile distinct from developer/user Codex, Claude, Grok, or Google homes. Never change the machine's global environment or default provider settings. ## Distribution and desktop channel requirements

I01 selected no runtime. I10 now pins Codex CLI 0.160.0 as a development dependency and resolves its documented optional-package binary for macOS arm64/x64 or Windows x64. Packaged resolution is deliberately unavailable until the distribution/isolation/signing work in the runbook is complete. An enabled distributed adapter must record exact package/binary versions, OS/architecture support, upstream license/notice locations, redistribution basis, signature provenance, runtime resource locations, and update policy. Prefer an approved bundled runtime for predictable desktop UX; an installer script or executable found on PATH is not a trustworthy distribution contract. If redistribution is unavailable, record the dependency and its UX consequence rather than adding a silent downloader.

Direct macOS arm64/x64 and Windows x64 are the intended first targets, subject to each chosen runtime's actual support. Existing signing/notarization/native gates remain. Microsoft Store's selected EXE route uses the same direct artifact and requires its independent review; it does not grant provider rights. MAS remains unsupported/blocked by existing native requirements and is not enabled by a working direct provider. Linux/WSL instructions in upstream documentation do not expand Collie's product scope.

Disable runtime self-update/background downloads through supported configuration or hold packaging unresolved. Grok documents `--no-auto-update` for headless/ACP use; this is useful evidence, not a complete packaging decision. [Headless integration](https://docs.x.ai/build/cli/headless-scripting).
