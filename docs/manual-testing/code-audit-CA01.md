# CA01 — User acceptance guide

**Implementation complete — awaiting user testing.** Format, lint and typecheck pass. Runtime and native-file observations below have not been performed by the assistant. Use the [implementation record](../validation/code-audit-CA01.md) for scope and limitations.

Use a disposable project and a new output folder. Keep valuable originals outside this exercise. From the repository, use the documented Node 24.21.0/npm 11.19.0 setup and launch with `npm run dev`; launch is your step. A project with editing access is needed. Single-format exports do not require enabling an unavailable paid or provider route.

1. **Fresh exports.** Create a short document with headings, ordinary text and an image with alt text. Open Export and follow its options, preflight and destination steps. Export DOCX, PDF, Markdown and text separately with a different fresh name each time. Each successful file should show `complete`, with the batch phase `All selected files ready`. Open each in its normal reader. Review declared format losses; successful publication does not imply identical formatting across formats.
2. **Markdown images.** Inspect the Markdown output and its adjacent `<base name>-assets-<job ID>` folder. Open the document in a Markdown reader supporting local images. The referenced image should exist and display when the document and folder stay together.
3. **Existing destinations.** Repeat an export into the same folder with an already-used base name. The existing file should stay intact; results should identify the collision, including `Existing output kept. Choose another name or folder.` where worker publication reports it. Choose a fresh name for the next export.
4. **Partial completion/cancellation.** If your existing access permits multiple formats, export a disposable image-rich document to several formats and use `Cancel remaining export work` while it is offered. Earlier completed files should remain complete; remaining work should be cancelled. If a destination or image directory was already created before cancellation/failure, its result should describe the retained artifacts. Keep the folder with the report for review. A very fast export may complete before cancellation; all-complete is valid. Do not induce disk failures, kill processes or modify files mid-publication just to force this case. Leave unobserved failure branches pending.
5. **Writing and native editor actions.** Type in two sections, switch sections, open/close the writing side panel and use Find, Undo/Redo and plain-text paste. Selection and content should stay with the intended section; opening a panel should not recreate the editor or erase undo history. Pause briefly after editing, then use Save and reopen the disposable project; protected writing should remain. First Save should ask for a destination; later Save should update that assigned project file.
6. **Draft and navigation continuity.** Enter unsaved text in project details, a note and a source/evidence form one at a time. Attempt navigation, then follow the offered save/discard/stay choices. Drafts and any visible retry action should remain until resolved. Follow a note/source/evidence link and rapidly choose another destination: the latest destination should win without a delayed earlier selection replacing it.
7. **Footnotes, sources and export choices.** Open a footnote/citation from a reference link, then return to writing. Open a disposable PDF source and change pages or excerpts. The selected target and visible text should agree. In Export, obtain a preflight, then change the selection or options; the previous preflight/acknowledgment should no longer authorize the changed export.
8. **Preferences and local AI state.** Change appearance/zoom and writing-panel layout, then revisit the workspace; preferences should remain consistent. If saved conversation/review history already exists, switch between entries and disposable projects: the displayed entry, selection and draft should belong to the current project. This step requires no login, model discovery or inference. Unavailable provider features should remain unavailable.

Report which numbered steps you completed, the visible status/error text, and any differences between expected and observed behavior. Leave native formats, cancellation branches or gated features you could not observe marked pending. Release approval and later audit stages remain separate.
