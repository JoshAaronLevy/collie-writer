# PL05 — User walkthrough

Implementation and code checks are complete; runtime acceptance is pending. Perform these actions yourself, using disposable projects/copies for changes, migration and Undo.

1. Launch with your usual `npm run dev` setup. Open a disposable project with a few notes, sources and chats, and an existing chapter containing recognizable prose. Enter Plan → ChatGPT, select an eligible own-account connection/model, and choose **Suggest an outline**. Expect **Create editable outline** and collection analysis to be selected, with the request-budget notice. Send explicitly. Opening the project or changing scope should send nothing.
2. Open **Review outline** on the completed response. Expect coverage, editable chapter cards, purposes, named material references and development gaps. Check that existing chapters are identified as changes and new ones as new chapters/sections. The live outline and prose should still be unchanged. If the model returned invalid structure/references, expect a clear issue and retained original response; no partial outline or automatic repair request should occur.
3. Change two proposed titles and some material assignments, use earlier/later or parent/position controls, and remove an unwanted proposed change. Keep positions distinct within each parent. Save edits, Dismiss, reopen the response and select saved versions. Expect the edited version and original suggestion to remain separate; none of this should change the live outline. Repeat editing with keyboard navigation and a narrow window/200% zoom.
4. Choose **Keep discussing**, describe a refinement and Send explicitly. Expect the selected saved proposal to inform the new response. Reopen the older response: its edited version should still exist. Dismiss the new result and confirm that the accepted outline remains unchanged.
5. On a valid current proposal, review its coverage and optional editorial changes. If suggestions are present, explicitly select one and leave another unchecked. Choose **Use outline** or **Apply changes**. Expect the displayed chapter titles, purposes, order and assignments in both Plan and Write, once. Existing prose, unspecified chapters and unrelated links should remain. Only selected dispositions should change. Reopening the same response should show it as applied and offer Undo, rather than creating its chapters again.
6. On a separate disposable revision, ask to rename/reorder existing chapters while preserving their text. Apply it, then add a sentence to an existing chapter through Write. Return to the response → Review outline → **Undo outline change**. Expect the structural/reference changes to reverse while the later sentence remains. New empty chapters from an applied creation proposal should leave the active outline and remain in Trash. Save, close normally and reopen: the reversal and retained proposal versions should remain.
7. Use separate disposable copies for conflicts. Produce a proposal, then edit an analyzed note or a relevant chapter before applying. Expect a specific refusal preserving the newer work and saved proposal. Separately, apply a proposal, then change an affected title/link/disposition or write into a newly created chapter before Undo. Expect unsafe Undo to be refused as a whole, without replacing the newer work. Keep discussing should prepare a fresh request, never send it automatically.
8. If **Check change** appears after an uncertain acknowledgment, choose it before another action. Expect the original committed result to be adopted or a clear report that nothing was saved. It should not dispatch AI or create another outline. Save and reopen normally; completed applications and Undo records should remain inspectable from their response.
9. Save, open an independent disposable copy, and disconnect AI. Expect saved proposal versions, chapter/material links and eligible local Apply/Undo actions to remain available without AI. No copied request should restart. Under read-only project access, saved versions should still be inspectable while edits, Apply and Undo are unavailable. Existing History remains the separate whole-manuscript restore action.

Report the step, visible error and actual result. Code checks do not establish runtime acceptance. PL06’s generated-prose insertion is not implemented by this stage.
