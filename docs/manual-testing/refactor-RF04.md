# RF04 — Lightweight project discovery

Implementation complete — awaiting user testing. These are user-owned observations, not results established by source inspection or code checks. Use disposable projects and copies for Save, archive and compatibility observations. Do not damage working folders to manufacture a failure.

Stage RF04 complete. As a user:

1. **Launch normally** (for development, run `npm run dev` with the repository's pinned toolchain). With several existing projects, open **Projects** and use **Recent**, **All active**, **Archived**, the title filter and **Refresh projects**. Healthy entries remain available. The remembered project can reopen through its normal checks; broader recovery/space information loads afterward. No particular speed improvement has been measured or promised.
2. **Open an older local project**, including a disposable copy with imported chats, research and notes. Its title and date are listed before opening. An older entry may initially say **Project** instead of its specific type; after opening, returning to Projects shows its actual type. Writing, imported originals, relationships and saved conversations remain available. Opening does not send AI requests or accept prepared imports.
3. **Change a disposable project's title, Save it, and return to Projects.** Refresh shows the updated title and last saved filename. Archive and unarchive it through the existing project actions: the appropriate library view changes. An inactive row says **Last saved to…**; opening it establishes current file availability and whether newer local work needs Save.
4. **If a library-details warning occurs naturally**, open **Review recovery**. The affected title appears when readable, or an honest unavailable-title description appears. When one workspace is known, **Open project** attempts normal admission and refreshes the listing. A missing hint alone can be repaired this way; an actual content, ownership or storage problem remains an error. Other healthy projects remain selectable. Backup/version choices preserve the originals.
5. **Continue a retained New Project setup after restarting**, or create a disposable project and choose it for free editing. The existing project opens before editing access changes, and continuation reaches that same project's writing. It does not create a duplicate, report missing ownership as a storage-permission failure, or grant editing merely because an entry is listed. Opening the existing tutorial also reuses it; an unreadable hint alone does not create a new sample.
6. **If an uncertain Save already exists**, use its recovery action. A confirmed outcome clears only that exact Save; Refresh projects alone does not settle it. Save, Save As and Backup retain their existing destination and independent-copy behavior. Check that locally retained writing survives ordinary close/reopen.
7. **Use keyboard navigation and increased zoom** in Projects and, if present, recovery. Project rows, Refresh and Open project remain reachable and clearly labeled; closing recovery returns focus through the existing guarded behavior. Moving between Projects and writing preserves pending drafts and the chosen section.

The library intentionally does not establish that every listed database is readable. Full content admission and any required migration happen when that project is opened, or at existing explicit archive/recovery boundaries. A bad database may therefore be discovered only on Open. Root-level directory failures and the existing resource ceilings can still prevent a complete list. Native migration/recovery, visual accessibility and large-library behavior remain pending user observations; do not treat listing success as release acceptance.
