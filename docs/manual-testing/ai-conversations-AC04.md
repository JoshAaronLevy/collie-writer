# AC04 — Conversation memory

Implementation complete — awaiting user testing. Use disposable copies for migration/Save As/copy/restore actions. These are manual observations for Josh; do not run automated suites, generate bulk fixtures, fill quotas, edit databases or inject failures. If naturally long history or a sufficiently large outline is unavailable, leave those observations pending.

1. Save and quit the existing app normally, stop its old development process, then run `npm run dev`. Open a disposable copy of an existing project. Its old writing, research, conversations and AC03 drafts should remain available after the retained-copy migration. Opening alone should not send anything.
2. Open a short chat. The concise sharing explanation should mention possible extra requests for long context. Send an ordinary short message: it should go straight through the normal streaming loop without unnecessary preparation. Confirm the earlier AC02 completion fix still behaves correctly; prior acceptance is not assumed here.
3. In a naturally long chat, leave Project context or This chat only selected and Send a follow-up. When memory is needed, expect **Preparing context…** with Stop, then the original question and its streaming answer. There should be no separate approval form, no duplicate user question and at most two preparation requests. Completed preparation turns should stay collapsed.
4. Open **Context → Memory**. Inspect the current summary, its coverage description and **View originals**. Original exchanges/input and generated text should remain available. Ask about a real earlier decision and a recent detail: judge whether the answer uses both correctly. A summary must not be presented as a verified quotation or new research.
5. Edit a current summary and Save memory. Refresh/inspect memory: the new revision should be current, while Older versions still exposes its predecessor. Start another edit, close/reopen Context and confirm the unsaved edit remains. Save or Cancel before leaving the project; neither action should send a message by itself.
6. During another naturally needed preparation, click Stop. The original user draft, prior memory and any actual preparation output should remain. The original question must not send afterward. If you edit current writing or change the selected account/model during preparation through an available route, continuation should stop instead of silently using changed intent.
7. If your outline/description/synopses naturally require overview memory, inspect that checkpoint. Change a covered writing revision or relevant project metadata. Refresh Memory: old coverage should show **Stale, excluded**. The next relevant Send should regenerate necessary overview memory or use the current raw overview. It should not claim other manuscript bodies, research or other chats were read; those are AC05.
8. Choose **Message only**, then Send: no memory or prior history should appear in that message's sent snapshot. Choose **This chat only**: chat memory/recent exchanges may appear, while project overview/writing should not. Loading earlier transcript pages must not change either policy.
9. Save, quit normally, restart and reopen. Checkpoints, edits, originals and drafts should remain, with no preparation or message automatically resent. Export to a new filename: preparation entries should be labeled and memory revisions retained; Export with sent context should additionally preserve the exact snapshots. On a disposable copy, use the normal independent-copy or backup/restore flow and inspect the same material.
10. Use a narrow/zoomed pane and keyboard navigation. Context/Memory and its editor should stay usable without obscuring ordinary chat. IME composition must not accidentally Send, save or cancel an edit. After preparation, typing during a normal streamed response should still preserve the next draft without queuing it.

If a real provider, storage, capacity or timeout problem occurs, the draft and prior checkpoint must remain, with actual preparation outcomes/recovery visible. An oversized recent exchange, current writing or legacy backlog should offer context narrowing/new chat rather than silently losing coverage or launching repeated summary jobs. Do not manufacture these conditions; report naturally encountered alerts and the preceding action.

Report success/failure separately for live answer completion, memory relevance, Stop/changed intent, Save/reopen/copy and keyboard/layout. Correct code checks do not establish these outcomes.
