# Stage 21 user-owned manual guide

Stage 21 local implementation complete. As a user:

**Signed distribution remains blocked until the external prerequisites and native observations in the [owner runbook](../release/direct-installers-and-updates.md) are satisfied.** The assistant did not create/run tests, checks, builds, packages, app launches or artifact inspection. Use disposable `.collie` copies and a working folder with no irreplaceable recovery for install, update, repair and uninstall scenarios.

1. When I open the current development build and choose Help → Check for updates, I should see “Updates are not configured in this build”; no update download or restart should begin. Help → Install downloaded update should say none is ready.
2. After I prepare a correctly configured and signed direct candidate using my own credentials, install it on a clean supported Mac or Windows computer, and inspect its OS publisher details, I should see the selected production or beta label, matching app ID/publisher and no global Node/compiler requirement. A missing signature, notarization ticket or expected native architecture blocks acceptance.
3. When I create a disposable draft, Save to a chosen `.collie` file, quit and reopen that file through the production OS association or the app's Open/Recent flow, I should find the writing intact. In beta I should use Open on a copy because beta does not register the default association. A simultaneous external file change should invoke the existing conflict choice rather than silently overwrite either copy.
4. When I choose Help → Check for updates on a configured release with no newer version, I should see an up-to-date message. With a newer signed release in that channel's owned feed, I should be asked before download and again before restart; doing nothing should not initiate a check. A beta package should not request the production feed, or vice versa.
5. When I deliberately leave an edit or file operation pending and choose Install downloaded update, I should be able to keep the window open or protect the writing first. After I explicitly allow restart and the storage close completes, the newer signed app should reopen with the saved file and any local recovery still available. Do not use valuable work to create this scenario.
6. When I interrupt a disposable download or temporarily go offline, the installed app and project should remain usable; retrying later should not silently install. A wrong-publisher, changed checksum, web installer, older version or off-channel artifact should be rejected without deleting the current app or data. Use only owner-controlled disposable release artifacts for this inspection.
7. When I uninstall and reinstall the same channel on a disposable computer, selected `.collie` files should still exist at their chosen locations, and retained local recovery should be available if the OS/uninstaller left that channel's app data alone. I should treat manual app-data deletion as potentially removing unsaved recovery. A beta or development installation should have a separate working location from production.
8. When I observe a failed installation or migration on a disposable older copy, the prior signed installer and pre-migration data copy should remain available for a reviewed repair. I should never open the only post-migration workspace in an older app or assume the updater can downgrade it safely.

Record actual platform, architecture, installer version/channel, signature/notary/publisher observation, update version pair, behavior and any failure without sharing writing, file paths, credentials or full update URLs. Empty or unconfigured feed results, signatures, native execution and interrupted-install outcomes remain pending until you supply observations.
