# Stage 23 user-owned release guide

**Stage 23 preparation is ready; release readiness is blocked and the stage is incomplete.** No signed candidate, authentic commerce setup or user-observed acceptance result is available. This guide describes expected outcomes, not recorded passes. It contains no request to run automated suites. The assistant has not built, launched or inspected the app or any output.

Use disposable local projects, copies of your own material or licensed public examples. Keep original files and an independent backup outside the disposable profile. Use a clean supported Mac and Windows computer with no irreplaceable recovery. Do not create faults by unplugging a disk during a write, editing databases/grants, deleting sidecars, corrupting archives or force-killing normal work. If a scenario cannot be safely observed through normal product controls, leave its gate pending. Purchases, hosting, participant contact and publication remain separate owner-authorized actions.

As a user:

1. After I supply the identity/signing prerequisites and prepare the direct candidates using the [Stage 21 owner instructions](../release/direct-installers-and-updates.md), I should have separately identified signed macOS arm64/x64 and Windows x64 artifacts. I record their actual version, source revision, filenames, hashes, signature/notary/publisher details and native architecture in the [manifest](../release/release-candidate-manifest.json). An absent or failed signature leaves the release blocked.
2. When I install the matching candidate on a clean supported computer and launch it normally, it should open without a global Node/compiler installation. I record OS/hardware/version and repeat the relevant journeys on the oldest and latest supported OS configurations; one machine's result does not establish the others.
3. When I disconnect the network and open the fictional Tutorial sample, I should be able to follow its writing/research/export path without an AI account. Creating a fresh tutorial should retain the previous sample and personal work.
4. When I create two disposable personal projects, each should initially have no selected destination. Canceling its first Save should leave recoverable local work and no chosen file. Choosing Save later should let me select that project's own `.collie` location; local protection, selected-file save and any later cloud upload should stay distinct.
5. When I choose a project for free editing, write and format a draft, add an image and note, reorganize the outline using non-drag controls, and inspect/restore history, the intended text and relationships should remain usable. A restore should create a new revision and retain the later work for inspection.
6. When I add a source with a disposable retained PDF/text original, inspect a passage, create an excerpt and link it to a question or claim and section, I should be able to return to that same evidence offline. Reimporting an edited original in a copy should retain prior excerpt evidence and flag relationships that need review.
7. When I search for known words in my disposable writing, notes and indexed retained sources, filters and result navigation should lead to the expected content. Extraction/coverage limitations should remain visible; an unindexed scan should not be presented as fully searched text.
8. When I insert citations and authored footnotes, move the cited writing and preview APA 7 or Chicago notes/bibliography, references and numbering should follow the captured selection. A broken reference should block export until repaired; incomplete metadata should require the implemented correction or explicit acknowledgment for that captured revision.
9. When I export DOCX and open it in current Word and LibreOffice, headings, section order, images, citations, bibliography, native footnotes, page breaks and non-Latin text should be readable. I record each reader/version separately and inspect Letter and A4. A required content or note loss blocks release.
10. When I export PDF and open it in independent PDF readers, the chosen paper layout, images, non-Latin text, citations and bibliography should be readable. Notes must be real page-bottom notes near their references; I inspect long notes and page boundaries for clipping or accidental endnotes. This result is still required for D5 acceptance.
11. When I export Markdown and plain text, the reports should describe the supported losses. Moving Markdown together with its adjacent asset folder should retain image links. Importing a disposable text/Markdown file should add new writing without replacing existing sections. Exporting and reimporting CSL JSON, BibTeX or RIS through the supported bibliography controls should preserve supported source metadata and report unsupported fields.
12. When I protect my draft, Save, back up and quit normally, then restore the backup on a different supported computer, I should find the writing, source originals, excerpts, notes, citations, outline/history and any existing recipes in an independent project. The restored project should not inherit the old computer's paths, free designation, credentials or license cache.
13. When I open a disposable copy of an older supported project, migration should create the current working copy while retaining the original/recovery material. If a migration or save naturally fails, the app should explain the failure and preserve the prior file and local work. I stop using the affected copy and report the visible behavior; unavailable interruption or disk-full scenarios remain pending.
14. When I save a disposable project to OneDrive, fully close it on computer A, wait for OneDrive itself to report upload complete, then fully download and open it on computer B, the latest writing should appear. The app must not claim it completed the cloud upload. I never use two computers to write the same file concurrently.
15. When an existing disposable cloud copy is unavailable offline, still downloading or externally changed, Open/Save should present an actionable waiting/error/conflict result without silently replacing the prior good file or newer local recovery. I keep both branches if a conflict occurs. If my cloud client cannot safely present these states, I leave them unverified.
16. When I switch the free editable project, the previous project's writing, source inspection, individual exports, backup and recovery should remain available. There should be no trial countdown, watermark, account requirement for reading, or automatic conversion to a purchase. An existing recipe should export one format at a time in free mode.
17. Only after authentic merchant/issuer setup and separate transaction authorization, when I follow the [Stage 20 guide](stage-20.md) for monthly/lifetime purchase and restore on Mac and Windows, I should receive the corresponding rights through the real provider path. Paid access should permit unrestricted projects, recipe changes and batches. Both approved USD offers cover the same nonfiction edition; lifetime includes future edition updates. Missing configuration leaves these observations pending, not simulated.
18. When a legitimately obtained subscription naturally expires, is refunded or passes its signed offline allowance, essential reading/export/backup/recovery should remain available and pending accepted writing should be protected. After an actual lifetime purchase and later edition update, lifetime rights should persist. I do not change the clock or edit access files to manufacture these states; unavailable transitions remain pending.
19. When I navigate the complete workflow by keyboard, with VoiceOver or NVDA where available, and at 200% zoom/high contrast/reduced motion, essential controls, focus, labels and status messages should remain understandable. I record platform/tool versions and any obstacle using the [accessibility matrix](../accessibility/stage-19-matrix.md).
20. When I request Support preview, only version/platform/storage/uptime and known error codes should appear, with no automatic upload. During normal offline work and any separately authorized checkout/update action, my owner-led privacy observations should show the disclosed local or metadata-only boundaries. I should see no ads, ad tracking, sponsored/affiliate placements or promotional upsells in free, paid, expired, tutorial, help, checkout or other controlled surfaces.
21. When I follow the [Stage 21 update/repair guide](stage-21.md) on disposable installations, checks/downloads/restarts should require the documented user actions, pending edits should be protected before restart, and same-channel signed upgrades should preserve selected files and recovery. Reinstalling should not be represented as reversing a data migration. I record actual update versions and uninstall/data-retention behavior.
22. When I use already available large disposable projects matching the plan's scale targets, I should see useful progress/cancellation and responsive writing. I report sizes and observed durations for open/save/search/export, including 200,000-word output and 5/10 GiB snapshots where available. Missing data or measurement capability leaves the respective budget pending; I do not generate datasets or run benchmark scripts for this guide.
23. After I explicitly arrange consented sessions with target nonfiction writers, I observe each person attempt the same offline loop using their own local copies or public material. I record anonymous task outcomes, output handoff quality, accessibility friction and paid-value comprehension using the [value-session guide](../research/stage-18-value-sessions.md), without collecting writing or identifying the participant in this repository. No participant has yet been contacted or observed.
24. When I review the candidate gate register and supply my actual results, every claim should map to the exact observed artifact/platform. Any unresolved data-loss/security/severe accessibility issue or missing mandatory direct result should keep the decision at NO-GO. Even after a GO decision, publication should wait for a separate authorization naming the exact artifacts, destination and feed changes; store approval and future AI remain separate.

Report the candidate version, OS/architecture, guide step, actual outcome and a content-free description of any issue. Do not send manuscripts, file paths, source quotations, recovery codes, private keys or full network logs. Retain your local originals; use the [support procedure](../release/support-and-incidents.md) if preservation or repair is needed.
