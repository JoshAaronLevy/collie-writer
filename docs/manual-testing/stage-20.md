# Stage 20 user-owned manual guide

**Local adapter checkpoint implemented; configured commerce remains blocked.** This is not a report of successful purchases or completed Stage 20 acceptance. The assistant did not create or run tests, checks, builds, app/service launches, webhooks or transactions. Use your normal local launch workflow and disposable projects. No deployment or payment is required for the first three actions.

As a user, with the current unconfigured build:

1. When I open Access → Direct purchase, restore and subscription management, I should see a clear unconfigured message and disabled purchase/restore controls. The app should not open a browser, start a trial or connect to a merchant on its own.
2. When I continue writing in my designated free project and read/export/back up another project, the missing purchase configuration should not block those existing capabilities. The separate tutorial sample should still open.
3. When I open Settings and privacy and prepare a Support preview, I should see the distinction between signed licenses, encrypted purchase connections and local writing. The preview should contain no purchase credential, customer reference, project text or filename.

The remaining actions are **blocked until** the owner resolves the [prerequisites](../commerce/stage-20-prerequisites.md), authorizes hosting and user-operated sandbox transactions, and follows the [operator setup](../../services/entitlements/README.md). Do not substitute live payments, synthetic keys/grants, fixtures or automated suites. Record actual platform, sandbox environment, action and result without secrets or writing content.

As a user, after an authorized configured sandbox is available:

4. When I choose monthly or lifetime, the system browser should open a session for that specific offer. Checkout should show the configured USD base price, actual taxes/total, no trial, ads or promotional upsells. Merely opening or closing checkout must not unlock paid features.
5. When I complete a genuine sandbox purchase, request and securely save the browser's recovery code, and return to Check completion, paid access should appear only after the service confirms completed payment and the app authenticates its signed grants. If payment is pending or declined, access should remain unchanged. A browser success message alone is not confirmation.
6. When I close/reopen the app during an unfinished session, Reopen browser session should return to the same pending session while it is valid. Repeating Check completion should not create duplicate purchases. After expiry I should be able to start a new session, with any actually completed purchase recoverable using its code or verified purchase support.
7. When I restore the same purchase on my own other Mac or Windows installation, entering the recovery code in that app's system-browser session should restore the same edition. No manuscript upload, fingerprint or project-count ceiling should be required. An invalid recovery code should leave access unchanged. OS credential-storage failure should block the connection without saving plaintext secrets.
8. When I cancel a monthly subscription at period end through Manage subscription and refresh access, already-paid time should remain. When I buy lifetime while subscribed, the app should still show subscription management and should not claim the subscription was automatically canceled.
9. When the owner processes an authorized sandbox renewal, payment failure, partial refund, full refund or chargeback and I refresh, the signed dates/state should reflect the verified payment record. Pending/rejected refunds should not revoke access; a full approved refund removes the affected purchase/period. Reading, export, backup and recovery should remain available. Any pending editable draft should remain visible for protection when rights change.
10. When I return offline after receiving a valid grant, lifetime access should remain available and subscription access should follow its signed paid-through/grace dates. A failed refresh should not invent a revocation or delete work. Offline devices cannot receive later refund decisions until they reconnect.
11. When I choose Disconnect purchase account, this computer's connection and pending session should clear. Cached signed licenses, writing and files should remain; recurring billing should continue until explicitly canceled with the merchant. If I disconnect offline, the UI should say remote revocation was not confirmed. I should be able to restore later with my code.
12. When the owner replaces a lost recovery code through verified purchase support, the new code should restore and the old code should fail. After an authorized real signing-key rotation, the updated app should continue accepting retained old grants and later authentic revisions. A damaged local signed-grant cache should be preserved for support, never silently cleared by Disconnect.

Provider webhook authentication, queue durability, duplicate/out-of-order delivery, revision replay resistance, reverse-proxy redaction, packaged private-key exclusion, required CSP origins, geographic setup and provider-controlled no-ads behavior remain explicit unverified gates. Request only non-sensitive operator observations; do not publish raw requests, bearer tokens, full portal URLs or recovery codes as evidence.
