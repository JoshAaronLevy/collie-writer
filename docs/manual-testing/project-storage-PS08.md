# PS08 manual guide — New archive compression

**Implementation complete — awaiting user testing.** Required code checks do not establish runtime acceptance. See the [record](../validation/project-storage-PS08.md) and [writer policy/space budgets](../formats/archive-compression-v1.md). Use disposable projects, ordinary content and copies of existing files. Keep originals separately. Do not edit ZIP entries/internal journals, generate workloads, fill disks, inject failures or run automated suites. Existing saved conversations can be checked without sending another AI request.

Stage PS08 complete. As a user:

1. When I run `npm run dev` from this repository myself and create/open a disposable text-heavy project with ordinary writing and research, **Save As** produces a new self-contained `.collie` through the normal native picker. Finder/Explorer reports its actual file size. If I have a genuine older stored archive of comparable content, I keep it and record the two sizes; there is no promised reduction percentage and no compression setting to enable.
2. When I close/reopen the newly saved file through normal **Open project file…** and its existing local-versus-independent-copy choices, saved writing, research, citations, managed attachments and any already saved conversation history remain available. I compare the same content with the original disposable project. A local copy being available is not by itself proof of a new file round trip; I use the normal independent-copy choice when offered to inspect the archive's contents.
3. When I open a disposable copy of a genuine pre-PS08 uncompressed `.collie`, it still passes ordinary opening and shows its saved contents. Opening leaves that copied file unchanged. When I choose **Save As** to another new file, the new file uses the current writer and can be opened normally. If I do not have an older genuine archive, I report compatibility as unobserved rather than constructing one.
4. When I Save and make a separate **Backup** of a disposable attachment-heavy project using real PDFs/images or other ordinary managed files, progress and the usual completion/selected-file status remain available. Opening the saved file and Backup through the normal choices preserves the attachments, writing, citation settings and already saved conversations. Backup retains its existing separate destination/lineage behavior. Its size may stay close to the originals because managed blobs remain stored.
5. Only when an ordinary disposable Save/Backup lasts long enough and **Cancel** is visibly available, I choose it before replacement. The job settles as cancelled, local writing remains available and the previous selected file remains usable. I keep a separate copy beforehand. Cancellation is unavailable once publication begins; an operation completing too quickly leaves cancellation unobserved. I do not force slowdowns or interruptions.
6. When I visit **Settings → Data and recovery** after an ordinary completed Save, external project-file lengths and local categories reflect their separate actual contents. A compact `.collie` does not imply equally small local data or no need for full validation space. Only if a real capacity failure occurs naturally, I follow its existing required/available-space explanation and recovery choices; local work/previous files remain protected. Compression adds no automatic cleanup.

Report observed size/content/cancellation results and any mismatch, keeping missing older-file, capacity, native-platform or cancellation observations pending. Runtime performance and release acceptance remain unverified. Stop after PS08; AI-powered import remains separate work.
