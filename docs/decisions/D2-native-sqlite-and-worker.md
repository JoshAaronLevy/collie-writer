# D2 — Native SQLite and utility process

**September 29, 2026. Implementation selected; native acceptance pending user testing.** This is a Stage 2 implementation checkpoint, not proof that a packaged binary runs on any target. The assistant did not build, launch, inspect an artifact, run checks or write tests.

## Choice

Pin `better-sqlite3` **13.0.3** as the sole production SQLite driver and `@types/better-sqlite3` **9.6.0** for development types. The installed package contains Node-API prebuilds for macOS and Windows on arm64/x64. Its bundled SQLite header declares **3.53.4**; the app requires runtime SQLite **3.51.3 or later**, FTS5 and Node-API **10 or later**. The version shown in the shell comes from the actual loaded engine after the worker opens an in-memory connection. The header/prebuild inventory is source evidence, not packaged runtime proof. See [upstream package](https://github.com/WiseLibs/better-sqlite3/tree/v13.0.3), [Electron utility process](https://www.electronjs.org/docs/latest/api/utility-process) and [electron-vite worker entry guidance](https://electron-vite.org/guide/dev#utility-process-and-child-process).

The app forks one Electron utility process after readiness. It receives one fixed initialization message with the selected native binding path and sends back a bounded runtime status. It has no renderer port, generic SQL command or project-file path yet. Main exposes only `storage.getStatus` plus a status subscription to the owning top frame; malformed worker responses or process exit make the status unavailable. There is no automatic restart or unknown-outcome write replay. Quit requests a bounded shutdown, then terminates an unresponsive child. Electron's utility process separates failure from the renderer; it is not a security sandbox.

The worker storage adapter is ready for Stage 4's trusted project path service. File connections enable `trusted_schema=OFF`, foreign keys, WAL and `synchronous=FULL`, and refuse a connection if required modes cannot be set. It provides synchronous transactional mutation with rollback on throw and a SQLite online-backup helper that opens the copied database and checks integrity and foreign keys. Stage 4 must establish verified device-local roots, command envelopes, revision/idempotency rules, writer ownership and recovery reconciliation before any manuscript data uses this adapter. The current application creates no project database and does not claim durable saves. SQLite's [WAL](https://sqlite.org/wal.html) and [backup](https://www.sqlite.org/backup.html) contracts still apply.

## Packaging decision

The dependency remains external to electron-vite's worker bundle. `electron-builder` v26 receives its JavaScript library as a production dependency and copies one target-specific `.node` file to `resources/native/better_sqlite3.node`; the worker supplies that absolute path through `nativeBinding` in packaged builds. The native file is outside ASAR, so no ASAR unpack rule is needed. File filters omit the unused prebuilds, native source/deps and compile-only `node-addon-api` package from the application payload. `allowMissingDependencies: false` catches absent production packages during the owner's package build. These configuration effects await artifact inspection. See [electron-vite dependency handling](https://electron-vite.org/guide/dependency-handling) and [electron-builder v26 file/extra-resource options](https://www.electron.build/v26/docs/api/app-builder-lib.interface.configuration/).

Keep `npmRebuild: false` and remove the old `postinstall` rebuild command because this selected driver ships Node-API prebuilds rather than Electron ABI-specific downloads. If a target prebuild fails to load or is missing, stop that target's acceptance. The explicit fallback is a source build of the pinned 13.0.3 package on that target with a pinned `node-gyp` and native toolchain, using its `build-release` script; place `build/Release/better_sqlite3.node` at `prebuilds/darwin-<arch>.node` or `prebuilds/win32-<arch>.node` before the user packages it. Record compiler/toolchain, binary origin, hashes and native results before accepting that fallback; do not silently switch drivers or ship an unverified binary. Windows arm64 remains a candidate, not a launch promise.

## Evidence still required

The user needs to build and open unsigned development packages on macOS arm64, macOS x64 and Windows x64, report the displayed runtime values and whether the worker exits with the app. The selected per-target binary and allowlist need user-owned package inspection. FTS queries, rollback, file WAL/FULL, online backup/reopen, native crash recovery and real project persistence are not observable from the current shell; they remain unverified until the Stage 4 product path and user feedback exist.
