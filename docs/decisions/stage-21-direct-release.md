# Stage 21 direct release architecture

October 1, 2026. Local implementation decision; native acceptance is pending.

Primary compatibility references: [electron-builder v26 auto-update](https://www.electron.build/v26/docs/features/auto-update/), [v26 macOS notarization](https://www.electron.build/v26/docs/notarization/), [v26 Windows signing](https://www.electron.build/v26/docs/features/code-signing/code-signing-win/), [v26 NSIS](https://www.electron.build/v26/docs/nsis/) and [Electron app lifecycle](https://www.electronjs.org/docs/latest/api/app). These inform configuration; actual artifact behavior still needs user observation.

Direct release uses the locked electron-builder 26.15.3 and electron-updater 6.6.2. The development builder file remains unsigned, uses `com.colliewriter.app.dev`, and has no feed. `electron-builder.direct.cjs` inherits the positive file/resource allowlist and selects either `com.colliewriter.app` or `com.colliewriter.app.beta`; its packaged public metadata supplies the matching runtime data-root identity. Production and beta use distinct installer names, Windows upgrade identities, local app/working roots and `/direct/<channel>/` feeds. A beta build requires a `-beta.N` package version; production uses a release version. No runtime environment variable, project file, renderer input or downloaded update can switch channels.

Supported initial direct targets are macOS 15+ on arm64/x64 and Windows 11 x64. A signed Mac build requires a Developer ID Application certificate, Hardened Runtime, notarization and stapling, and both DMG and ZIP; ZIP is required for the Mac updater. The existing JIT-only entitlement is retained. No camera, microphone, DYLD, unsigned-executable-memory or blanket library-validation entitlement is introduced. Windows uses a full NSIS per-machine installer, a verified publisher name, required code signing and signature verification on downloaded installers. Per-machine installation requires administrator approval, allows the `.collie` file association and may prompt again during updates. The Windows uninstaller is configured to retain app data; selected project files live outside it. OS and user actions can still remove data separately.

The update check is explicit in Help. Release metadata must name the package's exact HTTPS feed; an absent/mismatched configuration disables the updater. The updater session confines requests and redirects to that channel's origin/path and removes electron-updater v6's `x-user-staging-id` request header. Staged-percentage metadata is rejected. The library can create a local updater ID and cache, but no such ID is intentionally sent to the generic feed. Full downloads require a manifest SHA-512 and positive size for every listed artifact, followed by platform code-signature checks; Windows also requires the baked publisher name. Web installers, differential downloads and downgrades are disabled. No update installs automatically on quit. A requested restart uses the existing renderer flush, file-job and storage shutdown handshake before `quitAndInstall`. Local recovery is never treated as a replaceable cache. The app sends no manuscript, title, selected path, project identifier or content hash to the feed; the server still sees necessary network/transport metadata such as IP address, User-Agent, requested version/channel/platform manifest and artifact URL.

Direct publishing remains separate. There is no verified namespace/domain ownership, legal seller identity, signing certificate, notarization credential, Windows publisher subject, feed host or signed artifact in this checkout. The builder can only become a release path after those are supplied and independently inspected by the user. No installer, feed, update or native result is claimed here. A compromised feed could select any correctly signed artifact from the same publisher within a newer version; feed access and certificate/key protection therefore remain release operations. An update manifest is not separately signed under v26; a future migration to newer builder manifest signing requires its own compatibility review. Do not silently claim its v27 capability here.

The production `.collie` association opens enter main through Electron's OS open-file/second-instance events. Beta does not register the default association, so it cannot take it from production; use beta's Open command for a copied file. Main exchanges only an absolute `.collie` path for a short-lived grant bound to the current trusted window; the renderer uses the existing worker Open conflict and archive validation flow. The development package remains a separate identity. Repeated simultaneous OS open requests beyond one pending file must be retried through Open/Recent; no arbitrary command-line path becomes a renderer filesystem capability.

Updates never rewrite a selected project archive merely to install. Existing Stage 4–7 copy migration and retained recovery rules still govern opening a newer data format. A previous installer can repair application binaries, but it may not read a workspace migrated by a newer app; downgrade is blocked in the updater. Recovery from a bad release requires a preserved pre-migration backup/copy and a reviewed version-specific repair plan, not an automatic schema rollback.
