## Selected implementation

Use a small, independent Node service in `services/entitlements/`, with Node's built-in HTTP, crypto and SQLite interfaces. It has no npm runtime dependency and is outside the desktop build/packaging allowlist. This does not replace the Electron build, desktop SQLite worker or project schema. One service process owns one private SQLite database on local disk. A serialized reconciliation queue covers provider reads through purchase commits. SQLite runtime refuses older unfixed WAL versions. Production initialization creates service schema 1 only; unsupported schemas fail without a migration.

Main owns the HTTPS service origin and authentic issuer keyring. Renderer IPC exposes purchase/restore actions and bounded status, never a URL, customer ID, recovery code, grant, browser secret or bearer credential. OS-backed Electron `safeStorage` encrypts the separate purchase-connection file; macOS/Windows are required and unavailable encryption blocks new connections. No plaintext fallback. Signed grants remain in the existing access cache, separately from bearer credentials and project data.

Each user-initiated browser session has independent 256-bit browser, claim and device secrets generated in main. Only their SHA-256 digests go into the purchase database. The browser secret travels in a URL fragment, which the connect page removes before loading any provider script. The desktop claim secret cannot be obtained from that browser page. The service binds one session to the exact transaction it created; neither a query parameter, a checkout callback nor custom data alone can activate access. Explicit Check completion reconciles merchant state and returns signed grants. Claim retries use the same pre-generated device authority, so response loss cannot issue an unrelated credential. Twenty-minute sessions can be reopened after an app restart through the encrypted pending record.

Restore uses a high-entropy purchase recovery code, entered in the system browser. Its hash resolves the merchant customer and current purchases; it is not a signed grant or an email identifier. The purchaser saves the code in a password manager. Reissuing it replaces the previous code. There is no machine fingerprint or arbitrary device/project limit: each of the customer's Mac/Windows installations gets its own revocable connection credential. Connection credentials expire after one year without a successful refresh; expiry affects service authentication, not a cached lifetime grant. Lost-code replacement requires human purchase-ownership verification and the production support operation in the runbook. Store-channel restore is not implemented or promised.

Disconnect clears local encrypted connection state even when the service is unreachable, attempts remote revocation when possible, and reports when that was not confirmed. It does not cancel a subscription or discard cached signed licenses. Purchases under a new connection cannot invalidate unrelated local signed purchases.

## Payment authority and lifecycle

Only configured monthly/lifetime price IDs, quantity one, USD, automatic collection and a positive completed transaction are recognized. Catalog preparation checks $9.99/month and $199 one-time, active prices, no trials and no price overrides. Pending/failed payments never grant access. Zero-value completed transactions, including payment-method changes, are skipped and cannot create rights. Completed transactions with unsupported mixed baskets, manual collection or changed product semantics require purchase support; they are not silently interpreted as a paid offer.

Webhooks authenticate the timestamp plus **raw bytes**, with HMAC-SHA256, timing-safe comparison and a five-second timestamp tolerance. Event IDs are unique in a durable ledger. The handler records only the event ID, customer ID, occurrence time and processing/retry state, then acknowledges. It never stores the body. Processing re-reads canonical transactions, adjustments and subscriptions through authenticated Paddle API calls; an old event cannot overwrite rights with its historical payload. Failed reconciliation retains pending events with backoff. Explicit desktop refresh also reconciles, covering missed webhooks. Provider/network uncertainty never becomes a revocation.

Subscription paid-through comes from the newest non-refunded completed billing period, not a future invoice or `next_billed_at`. Current active/past-due renewals receive up to 14 days of signed grace. Canceled/paused subscriptions and scheduled cancellations retain already-paid time with no added renewal grace. Removing a refunded newer period does not reintroduce grace on an older one. Full approved refunds, cumulative partial refunds totaling the payment, and approved chargebacks remove the affected payment; rejected/pending/reversed adjustments do not. A partial refund below the full amount preserves access. A reversed chargeback can produce a later authentic active revision after canonical reconciliation.

The service atomically increments revisions only when a purchase decision or signing key ID changes. Every grant uses the existing flat, canonical Ed25519 [version-1 contract](../formats/access-v1.md). Lifetime has no expiry or app-version ceiling. The service records public key IDs to reject reusing an ID with different key bytes. Old verification keys must remain bundled during planned rotation; private keys stay solely in protected server storage. An offline device cannot learn about a later refund, credential disconnection or key incident until it reconnects.

## Feasibility evidence and outstanding gates

Primary documentation consulted October 1, 2026:

- [Paddle transaction creation](https://developer.paddle.com/api-reference/transactions/create-transaction/) and [transaction checkout](https://developer.paddle.com/build/transactions/pass-transaction-checkout/) describe creating a transaction server-side and opening that specific ID with the public checkout client token. Paddle supplies billing, while Collie's service supplies desktop grants.
- [Webhook signature verification](https://developer.paddle.com/webhooks/about/signature-verification/) specifies raw-body HMAC and timestamp handling. [Access provisioning guidance](https://developer.paddle.com/build/subscriptions/provision-access-webhooks/) describes duplicate/out-of-order events and canonical reconciliation needs.
- [Transaction listing](https://developer.paddle.com/api-reference/transactions/list-transactions/) provides customer/status filters, pagination and billing periods. [Adjustments](https://developer.paddle.com/api-reference/adjustments/list-adjustments/) exposes approval, reversal and full/partial refund state used by reconciliation.
- [Customer portal sessions](https://developer.paddle.com/api-reference/customer-portals/create-customer-portal-session/) provides authenticated management links; no link is issued without the customer's connection credential.
- [Checkout options](https://developer.paddle.com/paddle-js/methods/paddle-checkout-open/) documents transaction IDs and checkout configuration. The adapter does not enable upsells, discounts, trials, tracking custom data or saved-payment authentication.
- [Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage) and [Node 24 SQLite](https://nodejs.org/download/release/latest-v24.x/docs/api/sqlite.html) describe the selected native/built-in boundaries. Node 24 documents SQLite as a release-candidate API; the choice avoids another service-native dependency while keeping runtime acceptance pending. No runtime compatibility claim follows from reading these references.

Seller eligibility, domain approval, actual sandbox catalog, US market restrictions, checkout-required network origins, provider-controlled surfaces/scripts, and legal purchase copy need owner/provider review. Geographic restrictions are not implemented by the local adapter; a US address prefill would not enforce them either. No payment should be enabled until the owner confirms the merchant's geographic configuration; do not take payment and then reject the customer for geography. CSP deliberately fails closed until actual required checkout origins are known; do not widen it to arbitrary HTTPS. No ads, sponsored/affiliate placements, promotional upsells or advertising tracking may be introduced to resolve a provider limitation.

The source supports the integration architecture; D7's actual configured-provider demonstration remains unverified. No secrets, false seller details, sandbox fixtures, generated test grants, SDK installation, app/service launch, check or transaction was performed.
