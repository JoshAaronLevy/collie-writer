# D8 — Independently gated store distribution

October 1, 2026. **Channel decisions recorded; Stage 22 remains partial.** Microsoft Store EXE listing preparation uses the direct production release. Mac App Store implementation is blocked on missing native product code as well as external setup. Neither store has received a submission, passed review or supplied purchase/file-access evidence. Direct release readiness does not depend on either store.

## Selected channels

| Channel                         | Distribution, payment and updates                                                                                                                                                         | Current state                                                                                                                                                                     |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Microsoft Store, Windows 11 x64 | List the exact signed standalone NSIS production EXE also distributed directly. Retain the direct app identity, local data, Paddle purchase connection/restore and app-owned update feed. | Listing/configuration preparation only; signing, immutable hosting, configured commerce, native installation and certification remain pending.                                    |
| Mac App Store, macOS            | Electron MAS build with sandboxed file access, Apple non-consumable lifetime and auto-renewable subscription, native restore and Store updates.                                           | **Blocked: native entitlement and file adapters are not implemented.** Packaging deliberately refuses this channel and startup rejects MAS before profile/storage initialization. |

The Microsoft listing is another acquisition route for the same direct product, not a second purchase channel. There is no separate installer metadata variant, app ID, local database, feed, Microsoft receipt or Microsoft IAP adapter. Do not rebuild/re-sign an already accepted EXE for the listing: that would produce different bytes. The Store submission must identify the exact retained artifact. Microsoft-origin discovery does not turn a Paddle transaction into a Microsoft Store purchase.

Use `com.colliewriter.app` for direct production; keep development and beta identities separate. Identity control and registration still require the owner's verified seller/account details. A Microsoft EXE installation may update the existing direct installation because it is the same product. Switching between these acquisition routes must not relocate or delete work. A future MAS build uses its own sandbox container; no container migration or entitlement linking is implied by sharing the selected bundle identifier.

## MAS API decision

Electron's built-in [inAppPurchase](https://www.electronjs.org/docs/latest/api/in-app-purchase) can fetch products, queue purchases, restore completed transactions and locate an app receipt. Queue acceptance does not prove an entitlement. The installed Electron 44.5.0 types expose transaction IDs, date, payment and state; they do not expose verified expiry, revocation or signed current-entitlement data. [Apple's Transaction API](https://developer.apple.com/documentation/storekit/transaction) supplies verified transactions and current entitlements. A minimal StoreKit 2 bridge is therefore justified for those requirements. It is **selected future implementation work, not a bridge supplied by this stage**.

Do not add an unverifiable JSON adapter, generated signing key, receipt simulator or paid unlock. The existing shared capability policy remains authoritative. Authentic Apple results need a separate native authority path into that policy; they must not masquerade as direct Ed25519 issuer grants.

Required remaining entitlement implementation:

1. Add a bundled, signed native boundary with narrow main-only operations and an owner-confirmed product catalog. Map the Apple lifetime non-consumable and renewable subscription to the same nonfiction edition rights; there is no major-version ceiling on lifetime.
2. Obtain verified StoreKit transactions/current entitlements, enforce product/bundle/environment identity, and preserve expiration, revocation/refund and renewal semantics. Never unlock from an Electron payment-queue event alone. An unverified transaction or network error cannot manufacture or revoke rights.
3. Register transaction observation early; finish only the successfully delivered transaction after durable local entitlement handling. Handle pending, canceled and failed purchases without erasing free/recovery access.
4. Provide explicit native restore/synchronization and management, with device-local purchase evidence. Specify offline validity and clock handling through the shared policy; cached access cannot promise immediate knowledge of an offline refund. Preserve reading, export, backup, recovery and the free designation on loss.
5. Keep direct checkout, license import, direct update machinery and direct service credentials unavailable in MAS. No universal cross-store linking or restoration is selected.

## MAS file and sandbox work still required

The current direct filesystem implementation uses sibling staging and retained previous files. A selected-file grant does not establish permission for arbitrary siblings. Adding a bookmark flag alone would not make that writer sandbox-compatible. The fail-closed channel gate must stay until these product changes exist:

1. Use the MAS Electron runtime, correct sandbox/inherited helper entitlements and a local sandbox working root. Replace assumptions that shelling out to direct-build volume helpers or choosing an arbitrary working parent is valid inside the sandbox. No full-disk, broad home-folder or temporary-exception permission is selected.
2. Capture Open's `bookmarks[]` and Save's singular `bookmark` through the native picker. Keep bookmark records in device-local storage, never portable SQL/archives or renderer payloads. The installed Electron types and method-specific [dialog reference](https://www.electronjs.org/docs/latest/api/dialog) are authoritative; the page's generic bookmarks-array summary is inconsistent for Save.
3. Balance every successful scoped-access acquisition through completion, cancellation and failure. Electron's [scoped access API](https://www.electronjs.org/docs/latest/api/app#appstartaccessingsecurityscopedresourcebookmarkdata-macos) returns a release callback, not a resolved path or stale flag. Foundation's [bookmark resolution](<https://developer.apple.com/documentation/foundation/url/init(resolvingbookmarkdata:options:relativeto:bookmarkdataisstale:)-3ic6f>) must resolve moved URLs and renew stale data; unavailable permission requires a clear native reselection flow.
4. Replace the direct sibling-write path with narrow native coordinated replacement. Preserve the captured local candidate and a recoverable previous version; compare expected destination identity/content within the operation, refuse observed conflicts, and acknowledge only a committed archive. [Apple file coordination](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileCoordinators/FileCoordinators.html) supplies the native coordination model; it does not prove cloud compare-and-swap or upload completion.
5. Account for Electron bookmark Save creating an empty file before writing. Picker success or an empty placeholder is never a saved project. Cancellation/failure must preserve local work and cannot delete an unproven external file. Cover restart, moved files, repeated replacement, canceled jobs, permission renewal, local volumes and customer cloud folders.
6. Extend every applicable selected-file boundary: project Save/Open/Save As/Move/Backup/Locate/Recent and OS-open, import/source/image selection, compile output and Markdown sidecars. A folder grant for an explicitly selected output folder cannot become generic renderer filesystem access. Define access across the actual utility-process/native boundary instead of assuming a main-process bookmark grants every worker access.

The [Electron MAS guide](https://www.electronjs.org/docs/latest/tutorial/mac-app-store-submission-guide) requires the MAS runtime and appropriate signing/provisioning, distinguishes development from distribution signing, and documents the unavailable native updater. Native runtime/file/commerce behavior remains unobserved. Certificates alone cannot resolve the missing implementation above.

## External gates and purchase portability

Both channels need actual verified legal seller/support details, account/identifier ownership, approved US availability and accurate privacy/listing resources. Microsoft additionally needs the signed immutable artifact, retained hash/publisher evidence, standalone silent-install observations, owned HTTPS hosting and Partner Center review. Existing [direct commerce prerequisites](../commerce/stage-20-prerequisites.md) and the non-AI value decision remain closed.

MAS additionally needs the Apple team, development/distribution provisioning and certificates, registered products/prices, reviewed subscription terms, owner-operated signed sandbox/native evidence and eventual review. App-controlled surfaces and any selected commerce dependency must remain free of ads, ad tracking, sponsored/affiliate placements and promotional upsells. No additional store SDK or advertising dependency is introduced by this preparation.

One direct purchase is intended to cover the customer's Mac/Windows direct installations, including the Windows EXE obtained through Microsoft Store; actual configured restore remains unverified. MAS initially offers only its own proven Apple restoration when implemented. Portable `.collie` project copies carry content, not purchases, bookmarks or local recovery. Before a channel switch or removal, the user must retain an independently usable backup; deleting a sandbox container or app data can destroy unsaved local recovery.

See [listing/review preparation](../release/store-listings.md), [Stage 22 record](../validation/stage-22.md) and [manual guide](../manual-testing/stage-22.md). No tests, build/signing operations, launches, purchases, submissions or artifact verification were performed for this decision.
