## Delivered model and status behavior

`CodexAccountRuntime.models()` uses named `model/list` RPC on the **same** authenticated process that owns the isolated keyring session. No second credential owner, injected token, alternate provider, copied client ID or endpoint override is introduced. `LocalCodexSession.refreshModels()` runs only for an explicit user action, reads the account again, checks its saved label and process epoch, then accepts the bounded complete catalog. Reads/polling of Collie's status do not call it.

Catalog pagination limits total entries to 100, pages to 11 and each RPC to 20 seconds; repeated/invalid cursors, duplicate model IDs and malformed supported-text metadata are refused. Hidden and non-text models are omitted. IDs, labels, input modalities, default status and reasoning-effort values come from the runtime. The pin defines reasoning effort as an open string, so bounded actual values are retained rather than a fabricated enum. Collie offers no effort override and invents no model names or successful eligibility.

The [catalog processor](https://github.com/openai/codex/blob/rust-v0.160.0/codex-rs/app-server/src/request_processors/catalog_processor.rs) calls `OnlineIfUncached`; Refresh models means another runtime catalog read, **not guaranteed fresh network data** or an account entitlement check. Codex's already documented startup/background refresh may network while the explicitly started process lives. No hidden inference probe is used. Account/provider refusal may still occur on a future real request.

`ai-catalog.ts` owns exact transient catalog/readiness/selection validators. New named `ai.refreshModels` and `ai.selectModel` channels are validated in shared/main/preload together. Status distinguishes not loaded, loading, failed and loaded (including an empty list), with separate execution blockers and per-feature availability. Catalog entries and selection are in memory only, tied to the active connection and a new catalog revision. Selection requires that exact revision and a listed model; it performs no network action. Refresh retains an explicit selection only if still listed. Failure, process loss, close, replacement, disconnect or cleanup clears usable choices; there is no automatic replacement model.

The persistent account provider and Settings/setup/companion show **Refresh models**, a native Mantine select, the selected model/default effort and actual reasons requests remain unavailable. Pending work participates in the existing account/close owner and global progress. Local status polling repairs missed model-loading notifications; it never refreshes the catalog. Existing navigation, draft and IME/focus protections apply. Styles remain semantic and feature-owned; CSP is unchanged.

I12's old model membership check would enable Send merely from a catalog. Its legacy `aiModels` endpoint therefore remains empty for this route; real choices are exposed through connection status only. CD04/CD05 must replace that legacy behavior with authoritative durable execution eligibility. Main's v1 prepare/start is still registered-only. Neither existing feature receives accidental execution authority from the new UI.

## Delivered transport machinery and its present refusal

The account transport now bounds outstanding requests and stdin buffering in addition to newline framing, uses fatal streaming UTF-8 decoding, rejects malformed response envelopes, and retains process-loss/deadline behavior. Arbitrary server requests are rejected; during text work they also terminate the isolated child. No raw stderr, reasoning or provider diagnostics enter the renderer.

`executeText()` is a **main-only, currently refused** method on that same managed runtime. `requireLocalTextIsolation()` runs before any thread/content RPC and again at the dispatch boundaries. It is not the commercial `requireTextOnlyRuntime()`; both commercial funding/isolation refusals remain unchanged. There is no renderer raw-execution endpoint and no CD04 durable binding to this method yet.

Behind the unresolved gate, the implementation requests one fresh ephemeral thread, explicit app instructions and only the supplied bounded serialized text. It checks returned thread/model/provider/cwd/policy/instruction provenance, matches the process epoch, calls the main authorization callback before preparation and dispatch, and never uses resume/history APIs. It requests read-only tool networking and a default service tier; these settings are defense in depth, **not completed isolation**. It unsubscribes after a terminal result; that removes the connection subscription, not proof of secure runtime erasure. Runtime process/storage cleanup remains subject to the unfinished isolation design.

`CodexTextTurn` correlates the fresh thread, turn and message IDs, including notifications before `turn/start` acknowledgment. A completed RPC alone cannot settle a turn; an early terminal event waits for the matching acknowledgment. Deltas and canonical completed text share item identities and cannot append the same text twice. Unexpected tool items/rerouting, incompatible text rewrites, transport loss or timeouts preserve the bounded actual partial text and report failure/uncertainty. Output is at most 128,000 UTF-16 units across 64 visible agent items; final and commentary channels are separate. Exactly one completed, explicitly final item with no unclassified messages is needed for non-null `finalText`. Hidden reasoning is discarded. Structured schema identity, persistence of these channels and domain findings validation remain CD04/CD06 work.

One turn has a five-minute deadline; Stop sends one correlated `turn/interrupt`, then waits up to 15 seconds for terminal confirmation before retiring the child with uncertainty. No app-level fresh-turn retry, account/model fallback or automatic repair is implemented. The [provider defaults](https://github.com/openai/codex/blob/rust-v0.160.0/codex-rs/model-provider-info/src/lib.rs) allow four request retries and five stream reconnection attempts; the [client](https://github.com/openai/codex/blob/rust-v0.160.0/codex-rs/core/src/client.rs) also has authentication recovery and transport fallback. These native behaviors are not an exactly-once remote guarantee. On a reported retry/error, the handler requests interruption and preserves uncertainty; it cannot promise that interruption beats an already in-flight native retry. No normal-provider override is claimed to eliminate those behaviors.
