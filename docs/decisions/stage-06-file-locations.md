# Stage 6 — Native locations and save acknowledgment

**October 3 correction:** The [explicit Save and local recovery decision](save-and-local-recovery.md) supersedes this historical checkpoint's destination autosave, stale saved-generation veto and Save-on-close policy. Other file-safety and retention contracts remain.

September 29, 2026. Implementation selected; **native acceptance is pending user testing**. This extends D6 without changing archive v1, SQL schema 2, AST v1, dependencies or the build pipeline. No verification activity was performed.

## Location authority and opening

Main owns asynchronous native `.collie` Open/Save/Locate dialogs. It issues UUID tokens bound to purpose, project/workspace (where applicable), owning webContents and process/frame, with a ten-minute lifetime. A token can be retried only with its original operation ID. The bridge exposes named commands and bounded status, never an arbitrary path/SQL/IPC operation. Worker commands receive resolved grants from main. Direct desktop selections persist as local destination authority; MAS security-scoped bookmarks remain Stage 22.

`settings/picker-v1.json` remembers only the directory used to initialize a picker. Each workspace starts without `destination-v1.json`, meaning destination null. Picker acceptance does not create that file. Its acknowledged record contains the selected path, snapshot/head IDs, mapping generation UUID, native selection ID and fingerprint. Legacy schema-1 settings retain their unused null destination rows; no persistent SQL shape is altered or silently migrated in place. The new versioned metadata has its own strict reader. It never enters portable SQL.

Open first streams the selected regular file into device-local `file-operations/<operation ID>/incoming.collie`. OS reads hydrate cloud placeholders; progress and cooperative cancellation are visible. Archive validation/extraction uses that retained copy. Existing local work is never replaced by matching project ID. The inspection offers the existing local version or an independent incoming copy; an unknown project can instead open with its original identity and selected-file lineage. Copy promotion rewrites every project ownership key and ID-only operation receipt in an isolated validated database, preserves internal document/asset/commit identities within the new project scope, and records local origin. Copies start destination-null. This narrow incoming-copy action does not implement Stage 7's general Duplicate/Restore lifecycle.

Recent/local entries always open local working data and recheck the assigned file. Locate only rebinds an exact saved archive: project ID, snapshot ID, head and whole-file hash must match the current base. A different branch is an external change, not a moved-file match. Inspect/Open independent copy and Save As preserve the two branches; there is no merge or timestamp-based selection.

## Save protocol

1. The renderer serializes local commits and flushes the requested text, retaining exact operation IDs and unacknowledged buffers. Explicit Save waits for current file work; background destination saves coalesce to one operation after 30 seconds idle. An unassigned project never autosaves to a remembered folder. Stage 8 still owns the faster local-commit debounce.
2. A save checks the mapping generation, canonical parent, supported backing filesystem and full target generation (device/inode, length, nanosecond modification/change stamps and SHA-256). File bytes come from one opened regular-file handle, with before/after identity checks. Symlinks, hardlinks and access inside the working root are refused. Existing unrelated Save As targets require an additional native confirmation bound to the observed generation.
3. Persist a save intent in `file-operations/<operation UUID>/save.json` before capture. Use D6's shared capture boundary, coherent SQLite backup, minimum-head rule, leases and retained candidate. Archive work proceeds outside the mutation boundary so later typing/local commits remain possible.
4. Stream a sibling `.collie-<operation UUID>.staging` with exclusive creation, flush it, reopen through the full archive validator, and hash it again. For an existing target, retain and re-read `.collie-<operation UUID>.previous.collie` before replacement. Persist the replacement intent, then immediately recheck target generation and parent.
5. Existing-file replacement uses Node's same-volume rename: POSIX rename and libuv's Windows `MoveFileExW(..., MOVEFILE_REPLACE_EXISTING)` path. A missing target uses an exclusive hard-link publication followed by unlink of its staging alias, so a newly appearing foreign file cannot be clobbered. Unsupported link/replace operations fail without a fallback that truncates or unlinks the destination first. Cancellation ends before publication; the critical replacement/acknowledgment then finishes or leaves an uncertain intent.
6. Reopen the written archive, require the exact project/snapshot/head and candidate hash, and compare its generation again. Persist the destination record atomically, then acknowledge the intent. Only that captured head is saved. Save As keeps the project identity and switches mapping after acknowledgment; the prior path is untouched when a distinct destination was selected.

The [Node filesystem API](https://nodejs.org/docs/latest-v24.x/api/fs.html), [libuv Windows implementation](https://github.com/libuv/libuv/blob/v1.x/src/win/fs.c), and [Electron native dialog API](https://www.electronjs.org/docs/latest/api/dialog) informed these choices. These are API/source findings, not evidence of this app executing correctly.

## Interruption, retention and limits

Reopen/status reconciles journals without replaying writes. If the target validates as the exact candidate recorded by a replacing/replaced intent, it can finish the missing local acknowledgment. If acknowledgment already exists, the matching generation resolves the journal. Older intents cannot replace a newer mapping. Missing files, conflicting hashes, incomplete/corrupt journals or inaccessible old volumes stay unresolved; Save As remains available. A stopped first publication can remove only the proven identical staging hard-link alias before inspection. No recovery path guesses success or overwrites another file to repair uncertainty.

Completed candidates survive failed/unknown delivery. Previous siblings, incoming archives, interrupted staging and journals remain retained; there is no automatic expiry or cleanup UI in this stage. Successful Save removes its redundant capture/inspection/candidate copies after acknowledgment. Repeated saves therefore consume space for previous archives. Stage 7 owns inspectable retention/backup/recovery management and must not blindly remove these files.

The app's single instance, workspace ownership lock and one file operation coordinate this app/profile on one host. They do **not** lock out cloud clients, other programs, other release-channel profiles or another computer. An external writer can replace an existing file after the last comparison but before rename, or modify it after acknowledgment. An unobserved race cannot be claimed preserved by an ordinary rename API. All observed divergence stops overwrite and retains available versions; watchers, focus/resume, Save and reopen recheck. Cloud-client metadata-only/identity rewrites may conservatively require Locate even if content is unchanged. There is no upload-complete claim or cross-machine compare-and-swap.

Destination writes currently permit device-backed APFS/HFS+ on macOS (including removable volumes identified as such) and fixed NTFS/ReFS on Windows. Locally mounted OneDrive/provider folders on those volumes are allowed, independent of the stricter unsynced working-root rule. UNC/network, FAT/exFAT and unidentified write targets are refused with Save As guidance; Windows removable drives are refused. Actual cloud reparse points, permissions, hard-link support, atomic replacement and installed packages remain unverified. Windows directory flushing is not provided by the current Node adapter; sudden-power-loss durability remains a release gate on both platforms. The implementation does not run write probes.

Synchronous SQLite validation and OS-blocked file opens/reads may delay cancellation. Sleep requests a local buffer flush, including while a snapshot streams, but the OS need not wait for its acknowledgment. Close waits for local/file work and offers Retry, Save As, Keep open or explicit close with local recovery after local acknowledgment. An unavailable/unacknowledged buffer keeps the window open for copying. The close wait times out after two minutes into a keep-open notice; it does not kill a pending save. Rich editing, full recovery management, native associations and store-specific permissions remain in their owning stages.
