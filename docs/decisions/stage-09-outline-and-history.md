# Stage 9 — Outline transformations and human history

September 30, 2026. **Implementation complete — awaiting user testing.** No application, migration, archive or check was executed by the assistant. Native behavior, accessibility, conservation and storage costs are unverified.

## Outline and transaction boundary

Working SQL schema 3 adds the outline lifecycle, anchor registry and checkpoint stores; editor AST 1 and archive container 1 stay unchanged. Existing flat template sections keep their IDs, order and content. New parts and chapters are organizational containers with an inert blank payload; only `text` sections appear in the editor. Root accepts part/chapter/text; parts accept chapter/text; chapters accept text. Sibling positions are contiguous and include tombstones. A valid project always has at least one effectively active text section. Folder archive/trash state affects descendants without changing their individual lifecycle state.

`outline.change` supplies project/workspace scope, operation ID, expected project head, the complete document revision map, selected document and one strictly validated change. The serialized writer compares every revision and head before a transaction changes anything. The operation receipt uses the established portable ID-only shape. Exact retries reconcile the same operation; conflicting digests fail. A lost renderer response pauses editing and offers an explicit retry. New structural requests first flush document/metadata changes; stale comparisons require a fresh review.

Move/reorder preserves every block/citation/note identity. Split requires a stable top-level block boundary with blocks on both sides, retains the source identity for the first half and creates one new section for the second. Each footnote body travels with its reference. Merge appends source blocks after the target blocks, unions owned note bodies and makes the source a tombstone with a navigable replacement document ID. Its original content remains in the tombstone and pre-merge checkpoint; it is excluded from current occurrence indexes. Restore that earlier checkpoint to undo a merge. Synopsis/title/status remain inspectable in history; merge does not silently concatenate them into manuscript text.

For moves, splits, merges, archive/trash, details and anchor repair, production code compares sorted exact top-level block values and footnote ID/body pairs before and after. This covers nested block structure, text, marks, asset/source IDs, citation items/locators and note references. Ordering is applied by the explicit operation. Revisions change for modified documents/sibling positions; project head protects the entire tree. All current anchor and editor-ID projections rebuild in the same structural transaction. Ordinary document commits update only that document's projections.

## Anchors and manual repair

`anchor_targets` maps each block/citation/footnote ID to its current document, kind, effective lifecycle state, last bounded text context and optional explicit replacement anchor. Removed IDs remain `deleted`; moved IDs resolve to their new document. Archive/trash targets stay visible and can be restored. A merged document maps through `outline_state.replacement_id`, including later merges.

The history panel lists unavailable targets and opens their section or explicitly chosen replacement. Repair accepts a same-kind active identity selected by the user. No matching algorithm or text guessing runs, and repair never replaces manuscript text. If the chosen target later disappears, its status remains visible; a repair does not make that target active. Repair chains are cycle-checked and shown one hop at a time. A revived original block clears its own repair and resolves directly again. Text-range offsets and annotation content are Stage 10; this stage establishes identity/document mappings without inventing annotation/evidence tables.

## Checkpoints, restoration and cost

Every structural/repair/details action retains a protected pre-action checkpoint; restore retains the current manuscript first. Manual checkpoints carry a user label. Automatic human checkpoints are coalesced at 30-second intervals on the next acknowledged text or metadata commit. Current local commits remain durable between checkpoints; not every commit is a separately recoverable historical version. No timer claims protection of unacknowledged typing.

Checkpoints contain the complete outline, payloads including footnote bodies, anchor states and repair mappings. Their stored index points to immutable SHA-256-addressed section records in `history_content`. Unchanged sections and their anchor records are reused across checkpoints. Hashes stay local/in customer-selected archives. Structural/manual/automatic checkpoints use the same materializable contract; an arbitrary old commit alone is still not a historical export source. Project title, save location and the asset inventory are outside manuscript restore; retained managed assets are never removed.

Restore appends a new domain commit with new document revisions. It preserves every later checkpoint and operation receipt. Document identities introduced later remain as trashed blank tombstones; their actual later text stays in the protected pre-restore checkpoint and can be restored. This avoids duplicate live block identities when an earlier snapshot moves them back. Comparison shows text, outline paths/order, lifecycle, synopsis/status, block types and formatting/reference counts side by side. It is a readable comparison, not a word-level redline or rendered historical editor.

Retention is deliberate, never scheduled deletion: only automatic checkpoints older than 30 days are eligible, excluding the newest checkpoint and the current head. The user reviews a head-bound size/count preview before removal. Manual and pre-action checkpoints are protected. Cleanup deletes eligible checkpoint indexes and only section-history chunks no remaining checkpoint references. It never deletes current documents, blob bytes, saved files, migration copies, recovery, current evidence or active snapshot copies. Checkpoint parent IDs are immutable lineage labels; a parent can have been deliberately pruned. SQLite may reuse free pages without shrinking its file.

Provisional resource ceilings: 10,000 outline items; 1,000,000 retained anchor identities; 100,000 checkpoints; 256 MiB materialized content per checkpoint; the existing 4 GiB portable-database bound still applies. Limits fail explicitly and leave current buffers/originals retained. Size preview reports UTF-8 checkpoint indexes plus distinct retained section chunks, excluding SQLite overhead, blobs, working data and retained migration copies. A checkpoint selector's “index” size is just that index. No fixed daily growth, space-reclamation guarantee or responsiveness claim is made. Final retention budgets require user-reported ordinary/large-manuscript growth; do not substitute a benchmark or generator.

## Format compatibility and pending acceptance

The registered 2→3 migration runs on a backed-up candidate, seeds current anchors and an adoption checkpoint, validates the candidate, and publishes the active pointer only afterward. Schema 1 follows 1→2→3. Original databases, backups and failed candidates stay. New archive manifests declare schema/minimum reader 3 with editor/container 1. Prior schema-2/container-1 archives remain readable, are validated before promotion, and migrate in the local workspace; selected archives are never migrated in place. Independent copies re-scope all new table rows and ID-only receipts; internal document IDs and section-content hashes remain valid within the new project.

All managed assets still travel with every snapshot, including assets only used in retained history. Portable validation resolves history chunks, validates materialized snapshots and references, and refuses missing/corrupt/orphan chunks. Source/citation ownership and production citation/footnote editing remain later stages; their structural acceptance is unverified, not replaced by synthetic UI. No test code, fixture, probe, check, build or launch was added or run. See the [manual guide](../manual-testing/stage-09.md).
