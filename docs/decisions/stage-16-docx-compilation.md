# Stage 16 — Frozen compilation and DOCX publication

September 30, 2026. **Implementation complete — awaiting user testing.** The requested stage uses the Stage 3 `docx` adapter and Stage 15 pinned offline citation profile. This is an implementation decision, not a Word/LibreOffice fidelity result.

The renderer selects active writing sections, can toggle their chapter/part groups, orders the selected sections and chooses US Letter or A4. Before preview and before export, it protects pending source, note, writing and section-metadata drafts. The repository serial boundary reads the current head, selected AST, source metadata/style and exact managed image bytes; each image is length/hash checked and held in memory for the job. No later project mutation can alter this captured input. A job may render while the user keeps editing; the exported head is reported separately from the selected project-file save state.

Compilation model **version 2** adds source-map references for selected blocks, generated outline headings and footnotes. The canonical editor AST remains version 1; working SQL remains version 8; portable archive remains version 1 with minimum reader 8. The optional hierarchy headings in compilation are derived from selected active part/chapter ancestry. DOCX uses real next-page OOXML sections plus native styles, numbering, tables, image drawings/alt text/captions, page fields, page breaks, notes and bibliography. The same frozen model remains the input contract for Stage 17 PDF/text work. No citation-manager field or Word round-trip promise is made.

Preflight is scoped to the selected ordered sections. Missing/retired sources, missing/changed/oversized images and unsupported compilation block export. Incomplete or unreviewed metadata is listed separately and requires an explicit acknowledgment tied to the preview digest and captured head. No lossy conversion is currently allowed; any nonempty loss list disables export. Pinned retained CSL bytes, not updated installed styles, drive numbering and bibliography. Export reports in the device-local workspace retain the captured head, options, counts, issues, acknowledgment, source-map IDs and image hashes without uploading content.

The native dialog supplies the DOCX path; the renderer never supplies a filesystem path. An existing DOCX requires explicit replacement confirmation. The worker compares the observed destination identity and SHA-256 before staging and again before publication, writes a candidate in its private workspace, reads its OOXML container before publication, then publishes a same-directory staged copy. The prior DOCX is retained beside the destination with a unique `.previous.docx` suffix. A no-replace hard link prevents a newly appeared target from being clobbered. Failures and interruptions retain reports/candidates conservatively. There remains an unavoidable race with unrelated external writers between comparisons and filesystem operations, as with the existing selected-file workflow; no cloud compare-and-swap is claimed.

Rendering exposes phases and cancellation until publication starts. DOCX packaging itself is not preemptible; cancellation is honored before publication. After publication begins, completion or interruption is recorded rather than silently discarding an ambiguous result. This stage adds no PDF/text export screen, batch command, persistent compilation cache or project-file save acknowledgment. No tests, checks, app/browser launches, golden artifacts or viewer inspections were created or performed by the assistant under P7. Native reader fidelity, collision behavior, responsiveness and large-output limits await Josh's manual evidence.
