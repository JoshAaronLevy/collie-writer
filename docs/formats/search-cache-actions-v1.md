# PS04 search cache actions v1

October 5, 2026. Device-local maintenance only. Portable SQL/minimum reader **13**, AST/archive **1**, compilation **3**, saved project content, Save journals, snapshot leases and AI formats are unchanged.

## Owner and eligible files

`search.cache` is validated at the shared, main, preload and worker boundaries. Inputs are `preview`/`status` with a project/workspace scope and UUID, or `clear` with the same scope/UUID and the worker-issued review UUID. No renderer path or category is deletion authority. Main classifies this as local maintenance available to read-only projects; it grants no editing rights. Preview/clear require the exact active repository owner, its project lock, no active file mutation and no busy snapshot job. Status reads only the original receipt without acquiring/opening another project.

The repository's serial boundary covers preview and the entire clear operation, including asynchronous receipt writes. Search batches use that same boundary. The review records the head, working database inode/device, active-pointer digest, workspace identity, exact search filename set and each regular file's device/inode/length/nanosecond modification/change timestamps. Reviews expire after five minutes; at most 16 live reviews are retained. Stale scope/head/mapping/file-set proofs require a new review.

The reporting registry remains separate from eligibility:

- Current `search.sqlite` needs the live LocalSearch owner's matching device/inode (including each sidecar identity captured by that connection), exact known search schema and matching local search job when one exists. An unloaded/unprovable current index remains retained: open Search, then return to Data to review it. Preview does not open or initialize SQLite on disk.
- Only `search.sqlite.retained-<UUID>` copies without sidecars can qualify. Inspection copies at most four files of at most 32 MiB each to memory, validates the known schema and finds the exact search job in this workspace's operations database. No SQLite connection opens the retained disk file. The in-memory buffer changes SQLite header bytes 18/19 to rollback mode as required for WAL-image deserialization; the on-disk original is unchanged. See [SQLite's deserialize documentation](https://www.sqlite.org/c3ref/deserialize.html).
- Schema proof accepts exactly the three search tables, five FTS shadow tables and known unique autoindex, with exact normalized definitions for the three root tables, supported search metadata and no extra objects. Missing/foreign job proof, failed inspection, unexpected schemas, oversized files and retained sidecar families stay retained.
- Symlinks, redirected ancestors, hard links, special files, unknown names and uncertain identities never qualify. One preview visits at most 2,000 directory entries and lists at most 128 search-prefixed entries; incomplete/unsafe-name listings disable eligibility. Other workspace content is outside this action.

After the durable receipt is written, the owner cancels active indexing, closes its connection and sets the live search owner to null. Only SQLite handles its own known WAL/SHM during close. The cache action never blindly unlinks sidecars; remaining/changed sidecars are retained and block main-file deletion. It records any checkpoint-induced main-file changes under the same owner before removal. Each main file gets a final synchronous ancestor/directory/file identity and sidecar check immediately before unlink. A replacement is never removed using an old receipt.

Project databases, originals/blobs, citations, saved source pages/excerpts/corrections, writing/history, unsent drafts, saved conversations, credentials, AI journals/output and snapshot leases are never candidates. No VACUUM, recursive deletion, quarantine move, project migration or blob collection is performed.

## Durable receipt and client recovery

`<workspace>/cache-actions/<action UUID>.json` is `{ version: 1, view, files }`. `view` contains exact operation/scope/review/head IDs, workspace display path, time, completeness and the reviewed names/lengths/statuses/reasons. Each `files` entry repeats its view and contains its identity proof or null. The receipt lives outside all removal targets. Atomic same-directory temporary write, file synchronization, rename and the existing directory-sync helper precede cancellation/close/removal. Per-item updates follow each outcome; an interrupted receipt is not deletion authority.

Statuses are **eligible**, **retained**, **removed**, **absent** and **unknown**. The whole phase is **preview**, **complete**, **interrupted** or **not-started**. A completed action can contain unknown or retained items; completion describes settled processing, not universal removal. Replay/status only reports the receipt; it never repeats deletion. An eligible item left in an interrupted receipt is presented as unknown. A missing receipt is reported as not-started (no durable start record) only after the serialized command has settled; no removal is confirmed from receipt absence. This cannot prove historical non-execution after external receipt loss or platform persistence failure. An unreadable/missing workspace or invalid receipt is an error, not successful clearing. A new explicit preview/confirmation is required for remaining files.

Receipts are read with a 256 KiB limit and exact version/scope/shape validation. The folder admits at most 128 entries, including leftover atomic-write temporary files; reaching the limit refuses a new action before mutation. Receipts do not expire or self-delete. Temporary/unknown records remain unclassified in inventory; recognized receipt names count as local metadata/operations. Future receipt retention needs a separate reviewed policy.

Before dispatch, the retained Data owner saves one bounded exact clear request in `collie.search-cache-action.v1` (at most 2,048 characters, strict input validation). Failed local protection prevents dispatch. Unconfirmed replies keep the exact pending request and close/project-replacement/access guards; **Check outcome** issues status, never another deletion. Renderer recovery/restart can load that request. A malformed record is retained and disables new clearing rather than guessed or replayed. An authoritative result retires the local pending marker; failure to retire it retains Check outcome. No automatic mutation or status polling occurs at launch.

## Search lifecycle and reporting

Opening a project no longer creates a search connection. Entering Search or explicitly querying/refreshing/rebuilding it opens the index and schedules appropriate local work. Activity polling only observes. Hidden Search never queries or restarts indexing; it polls only an already observed running/queued job, so its operation guard can settle. Existing cancelled/interrupted jobs still require the existing explicit controls; they are not silently replayed. Queued callbacks see the cleared null owner and cannot rebuild it.

The confirmation shows exact reviewed names, estimated lengths and retention reasons. The result distinguishes confirmed removal from absence after SQLite close and uncertain outcomes. An outcome triggers a fresh inventory while Data is visible, or on returning there if navigation occurred. No full cache rebuild is triggered by inventory or Data visibility. Length sums are not physical reclaimed-space promises; SQLite checkpoints, sparse files, filesystem snapshots and OS caching can make them differ.

Node provides no portable atomic conditional unlink tied to an inode. Collie serializes its own readers/writers and leaves no asynchronous gap between final checks and unlink, but cannot exclude a hostile external process racing filesystem changes. The existing helper syncs directories on macOS; Windows has no Node directory flush guarantee here. Unexpected I/O/sync/receipt outcomes remain unknown, never automatically retried. Native macOS/Windows behavior and interruption handling remain user-unverified; this stage does not resolve CA03 or authorize PS05–PS08 retained-content cleanup.
