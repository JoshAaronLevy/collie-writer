# Signed access and device policy, version 1

Stage 18 introduces no project-format migration: working SQL/minimum reader remain 9, AST and archive container remain 1. Two new device-only files live in `access/` under the verified local working root. They are outside the project database, managed blobs, history, snapshots and reset-workspace directories. Picker cleanup and project reset do not remove them. Creating a missing version-1 file is initialization, not a content migration. Future format changes must retain the previous files and use copy migration; unknown/corrupt versions are preserved and do not get overwritten.

`capability-settings-v1.json` contains exactly `version: 1`, a UUID `revision`, and nullable `freeProject` and `sampleProject` scopes. Each scope contains only project/workspace UUIDs. This is local UI policy, never entitlement-service metadata. Stage 19 must register its own app-created sample through trusted main code; there is no renderer-supplied sample flag. Destination/title changes do not affect designation. Independent restored/duplicated workspaces do not inherit it. If a designated project is absent, users may explicitly designate another discovered project.

`entitlement-cache-v1.json` contains exactly `version: 1`, integer Unix-millisecond `lastSeen`, and up to 1,000 latest authentic signed documents, one per `(issuer, channel, purchaseRef, editionId)`. Cached documents are reverified on startup. The maximum issuer revision and any revocation remain in the signed document, not an unsigned override. The cache has no project IDs, titles, paths, content hashes, credentials or content. Writes use an exclusive sibling temporary file, file flush, rename and the existing platform directory-sync helper. A failed write does not acknowledge a new grant. Windows/native persistence acceptance remains pending.

If persisting a newly authenticated issuer decision fails, paid access becomes unavailable for the running session and further imports stop. This avoids continuing superseded rights after an authentic revocation or activating new rights on an uncertain write. Existing files remain for reconciliation on restart; reading, exporting, recovery and separately stored free designation remain available. A restart can only recover the authentic revision actually persisted; no offline application can promise durable revocation after storage failure or owner-controlled file rollback.

The signed envelope has exactly `grant` and `signature`. `signature` is canonical padded base64 of the 64-byte Ed25519 signature. `grant` has exactly:

| Field | Version-1 rule |
| --- | --- |
| `schema` | Integer `1` |
| `keyId`, `issuer`, `purchaseRef` | Opaque ASCII `[A-Za-z0-9_-]`, 1–128 characters; no email or content identifiers |
| `channel` | `direct`, `mas` or `microsoft`; must match the bundled key's authority |
| `editionId` | `nonfiction` |
| `accessKind` | `subscription` or `lifetime` |
| `revision` | Positive JavaScript safe integer, increasing monotonically per purchase identity |
| `status` | `active` or `revoked` |
| `issuedAt` | Exact UTC `YYYY-MM-DDTHH:mm:ss.sssZ`, a valid round-tripping date |
| `paidThrough`, `graceUntil` | Required only for subscription, same UTC syntax; grace is between paid-through and 14 days after it |

Lifetime documents must omit both subscription dates; no version/edition-upgrade ceiling or artificial lifetime expiry field is accepted. Extra fields are rejected. An active document issued more than five minutes in the future is unavailable until time catches up. An authenticated revocation takes effect when received. A later authentic active revision may restore rights; replay of an older active revision cannot undo the revocation.

Sign only the UTF-8 encoding of `grant`, serialized with ASCII property names sorted lexicographically, ECMAScript `JSON.stringify` scalar encoding and no whitespace/newline. The closed schema has no arrays/nested objects, floating-point numbers, non-ASCII strings or optional nulls, so this is a bounded RFC 8785 subset. Neither the envelope nor its signature field is signed. All authority fields, including key ID and issuer/channel, are signed. The app verifies with `crypto.verify(null, bytes, trustedEd25519Key, signature)` and never implements signing.

Trusted keys are build-owned entries in `src/main/entitlements/keys.ts`; they may contain public SPKI PEM only. Never load trust anchors from a project, imported document, renderer, environment override or checkout redirect. The keyring is currently empty because authentic issuer keys are not available. Stage 20 must supply real issuer configuration and genuine user-owned acceptance evidence. No key or grant examples are generated by this stage.

The renderer sees only a bounded `AccessView`: policy revision, state/capability flags, dates/warnings, local designation/sample scopes and an optional transition ID/scope. Signed documents, opaque purchase references and public-key configuration stay main-only. The native importer reads a selected, bounded access document and verifies it; user-facing errors do not log the document or filesystem path. There are no new network requests or secrets. Signed documents are not bearer restore tokens; Stage 20 must store those separately in OS-protected credential storage.
