# PS02 transient storage inventory

October 5, 2026. This describes the new bounded reporting protocol, not a portable or persistent format. No project schema, archive, recovery journal or account format changes.

PS03 extends the transient reply with separate volume capacity and whole-inventory condition readings; see the [storage advice/space addendum](storage-notices.md). Its notice preference is device-local and non-authoritative. The original measurement/deletion boundary below remains.

## Ownership and reporting boundary

`storage.inventory` accepts only `{ requestId, input }` from the trusted app frame. `input` is exactly Start (`kind: start`, new scan ID), Page (`kind: page`, scan ID, offset), or Cancel (`kind: cancel`, scan ID). IDs are validated UUIDs. Page offsets are nonnegative multiples of 25, bounded to 5,000. Renderer input carries no paths, sizes, ownership declarations or deletion grants. Preload validates requests and results; main validates the sender and request; main and worker validate their transient protocol/results.

Main supplies the worker's working and application-profile roots at initialization. On Start it separately supplies at most 512 operation-ID/scope pairs from the AI owner's already validated in-memory records. The renderer cannot supply that list. This lookup does not initialize accounts, load history, decrypt additional records or mutate AI operations. Unknown/cold/credential/runtime/candidate files stay shared/unattributed. Known operation files can contribute to their recorded project's working total, with their actual shared AI folder shown as the category location. This is recorded ownership, not validation of current ciphertext or removal authority.

Inventory requests have their own bounded pending map (four replies, five-second reply deadline). Worker messages are handled outside the authoritative project command queue. The scanner never acquires a project, opens SQLite, calls the recovery overview, reconciles a journal, extracts an archive, invokes a provider or writes files. It has no effect on editing/access authority or dirty/close protection. Existing recovery refresh/inspection/reset actions retain their separate behavior; the old recovery overview still has its own reconciliation semantics.

## Measurements and bounds

One transient scan is retained per worker. Refresh uses a new ID, cancels and drains the old scan before replacement, and does not start simultaneous scans. A scan expires after 30 seconds, with a 200,000-entry bound, 5,000-group bound, 48-level traversal bound, 64-volume bound and 128 categories per group. Directories are streamed and work yields between batches. Native filesystem calls already in progress cannot be forcibly aborted; expiry/cancellation marks measurements incomplete immediately and prevents further accounting. A replacement waits for those read-only calls to settle, with a visible reply failure if its five-second deadline expires. Shutdown cancels reporting without adding a writer/close blocker.

Results carry scan ID, running/complete/cancelled/limited/failed state, start time, last measurement time, visited count, repeated-reference count, separate working/application/external totals and at most 25 groups. Each group has a transient ID, recorded scope or null, local title hint, location, region, uncertainty note and categories. Each category has kind, location, per-scan volume label or unknown, measured bytes, file count and unknown-entry count. Result shapes and bounds are strictly validated. Reports exist only in memory and disappear on worker exit; they contain no file hashes, account labels or encrypted contents and are not added to diagnostics.

File lengths use metadata only. BigInt device/inode identities avoid rounding and count each observed physical file identity once across all roots and external references. Current working data is excluded from the application traversal; nested roots and repeated paths are not counted twice. Hard links with ambiguous ownership stay unclassified; unknown identities/sizes remain incomplete. Directory blocks, sparse/compressed allocation, clone sharing and filesystem metadata are not estimated. This is not an allocated-disk-space or reclaimed-space promise. A growing or replaced file can make measurements stale; start/as-of times describe a staged scan, not a coherent snapshot.

Links, redirected ancestors, special files, permission failures, unavailable destinations and excessive paths/depth are retained/unknown. Only known external paths from validated local destination/Save/Backup records are inspected, using file/ancestor metadata; no external directory is enumerated and no archive or cloud file is opened/read to measure it. Missing destinations/previous copies are unknown, not zero bytes. Metadata may still involve OS/provider latency. Unknown/unclassified bytes are never hidden or relabeled as cache. Limit/cancel/failure results remain visibly partial; unknown entries in a region conservatively qualify its group/category totals as incomplete.

Local project labels come from bounded `recovery.json` discovery records whose project/workspace IDs match the observed folder. Missing/stale labels grant no authority. Bounded metadata reads use read-only handles, reject links/hard links, check length/change and parse no more than 32 KiB. The active database pointer and destination/Save intent readers establish classifications and recorded locations without opening projects or changing journal phases. Invalid active pointers keep databases unclassified rather than assuming which one is current.

## Category policy

| Category                      | Reporting meaning                                                                                                                                                                                                                                          |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Project database and history  | The pointed working database and sidecars. Writing, research, citations, saved conversations and history share this physical total; no separate logical byte estimates are invented.                                                                       |
| Managed originals and images  | Managed hash-named blobs; original research and writing images share storage. Unknown files in that folder remain unclassified.                                                                                                                            |
| Managed citation files        | Saved assets within the citation owner.                                                                                                                                                                                                                    |
| Rebuildable search cache      | Exact current/retained search-index names and sidecars in an observed project workspace. This classification alone is not deletion proof.                                                                                                                  |
| Retained copies and recovery  | Project snapshots/migrations, retained incoming archives and reset recovery. Uncertain operation payloads remain retained/unclassified.                                                                                                                    |
| Local metadata and operations | Known workspace sidecars/metadata, settings and recognized Save/Backup journals.                                                                                                                                                                           |
| AI records                    | Attributed only through main's captured validated ownership; other encrypted data/credentials/runtime storage remain shared.                                                                                                                               |
| Application storage           | Profile, session, logs and crashes outside the working root. Other files are retained/unclassified.                                                                                                                                                        |
| Recorded external files       | Selected/previous/backup locations from local records. Current contents and actual archive ownership remain unverified, especially previous files replaced by Save As. Mixed recorded associations are unclassified; repeated identities are counted once. |
| Retained/unclassified         | Unrecognized files and ambiguous ownership. No cache/deletion implication.                                                                                                                                                                                 |

The shared typed `CACHE_CATEGORIES` registry currently contains only search, names its owner/reconstruction source, and explicitly declares clearing unavailable. PS02 has no cache-clearing or retained-content-removal action. Future PS04–PS07 must establish their own current owner proof and guarded mutations; this report cannot authorize them.
