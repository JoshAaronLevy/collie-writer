# PS06 completed local artifact retention v2

October 5, 2026. Additive device-local retention classes. Portable SQL/minimum reader **13**, archive/editor **1**, compilation **3**, snapshot journal **1**, Save/Backup journal **1**, leases, AI and credentials are unchanged. PS05's previous-version v1 receipts remain readable and unchanged.

## Supported removal matrix

Every supported row needs the shared prerequisites below. A file's location, age, terminal label or absence from a live map never supplies those prerequisites. The review selects **one regular file per confirmation**, not an entire folder. There is no recursive removal, automatic cleanup, expiry policy or Undo.

| Class                                            | Exact app-owned location                                            | Additional content proof                                                                                                                                                                                                                       |
| ------------------------------------------------ | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Transferred snapshot candidate                   | `workspaces/<project>/<workspace>/snapshots/<job>/candidate.collie` | Hash and length equal the fully inspected retained destination archive.                                                                                                                                                                        |
| Completed snapshot capture                       | Same job's `capture.sqlite`                                         | Hash and length equal that snapshot's database entry; no WAL/SHM/journal sidecars.                                                                                                                                                             |
| Completed snapshot inspection file               | Same job's `inspection/`                                            | Exact `manifest.json`, `project.sqlite`, `blobs/<hash>` or `citation-assets/<hash>` entry. Manifest must equal the inspected destination manifest; other files must match declared hash and length. Database sidecars refuse database removal. |
| Acknowledged Save/Backup staging inspection file | `file-operations/<operation>/stage-inspection/`                     | Same exact-entry rules and snapshot ownership.                                                                                                                                                                                                 |
| Acknowledged Save/Backup final inspection file   | `file-operations/<operation>/final-inspection/`                     | Same exact-entry rules and snapshot ownership.                                                                                                                                                                                                 |

Successful existing operations normally remove these copies already. PS06 addresses leftovers when the original cleanup did not finish; an empty review is normal. It does not start retaining new copies to populate the interface. Deleting an inspection entry may leave a partial inspection folder; the destination remains a separately validated complete copy. Empty directories and the original journals stay in place.

## Shared eligibility and actual owners

The worker derives every pathname; renderer input carries only the existing validated scope, action/review/artifact IDs and page offset through `project.localArtifacts`. The shared `RetentionInput`/`RetentionView` contract is reused. Main/preload/worker validate inputs and results. Main treats the action as local maintenance, with no editing grant.

Only the currently open project's exact workspace can preview/remove. The file maintenance guard settles an actual background file-check task, refuses other live file operations and blocks watchers/transitions. The awaited worker command and repository serial boundary hold the active project lock and refuse file, snapshot and export work. Additionally `SnapshotJobs.withRetention` owns its control queue and refuses an outstanding task, pending/active jobs or stopping. It holds that owner for the entire review/removal. A terminal event or main's caller timeout cannot release these owners. Search/repository mutations cannot interleave. CA03's general main bookkeeping remains unresolved; this is PS06's specific owner proof, not completion of that audit.

For each eligible file:

1. There is exactly one strict Save or Backup journal for its operation, in the reviewed project/workspace, with durable `acknowledged` phase and exact snapshot/job/head/hash references.
2. The snapshot owner returns a completed `done` job with no error, a released lease, a manifest and exactly one consuming operation. Its strict original disk journal equals the owner's validated in-memory record. Malformed startup records cannot match the conservative interrupted fallback. Coalesced, standalone, duplicate and untransferred snapshots remain protected.
3. That one snapshot request's ID, minimum head, parent lineage and digest match the Save/Backup request shape (including Backup's exact-head requirement). The full destination manifest matches the job manifest, not just a project ID or timestamp.
4. For ordinary Save/Move/Save As, the operation is the **current acknowledged destination generation**, with matching native grant, path, snapshot, head and hash in both disk and in-memory destination metadata. Older/detached generations are retained. Backup uses its own durable acknowledgment; its external output is never a removal target.
5. The destination path still passes the existing resolved external-file boundary. PS05's bounded, single-descriptor read-only archive inspector validates its hash, ZIP inventory, CRCs, payloads, citations, database and actual project identity. Nothing is imported, extracted, migrated or reconciled during preview.
6. The local target is a regular single-link file under unchanged non-linked ancestors. Its contents match the exact class rules above. Unknown entries, database sidecars and different bytes are not inferred disposable. Managed project blobs outside these inspection directories are never selected.
7. No prior removal is unresolved. Confirmed removed files that reappear remain protected, even with identical bytes. A receipt with a confirmed pre-unlink change permits a new review; unknown/interrupted/missing referenced receipts do not.

Review captures the current local head, destination, active-database mapping/pointer, disk destination metadata, original operation, snapshot record and target/replacement proofs. A local writing commit, destination change or relevant metadata change invalidates removal. Explicit unsaved renderer drafts remain owned by their retained editors; this action does not flush, save or discard them. File removal repeats full target/destination inspection and original owner checks under the same boundaries.

## Protected classes and expansion prerequisites

| Retained class                                                                             | Why it stays retained / prerequisite for any later extension                                                                                                       |
| ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Incoming archives, import/open inspections, `reconcile-*` folders                          | No durable, exact consumption/redundancy receipt for these payloads; require their original consumer to own and settle a compatible receipt first.                 |
| Untransferred/duplicate/standalone/coalesced snapshot candidates; provisional/exact leases | Released leases alone do not prove consumption. Need all consumer outcomes and complete retained replacement proof.                                                |
| Older Save generations or changed/unavailable destinations                                 | This stage does not traverse historical transfer acknowledgments to substitute another archive. Need an explicitly designed retained-replacement chain.            |
| Interrupted/corrupt/ambiguous journals or partial candidates                               | No verified completion or exact operation proof. Keep existing recovery and inspection controls.                                                                   |
| Export payloads and reports                                                                | CA07/CA08 operation identity and durable result recovery remain pending; CA01's implementation does not establish safe artifact disposal. No export deletion here. |
| Migration originals/backups and old databases                                              | Need migration-owner acknowledgment, compatibility and recovery retention rules; not merely a newer database pathname.                                             |
| Reset recovery and inactive working copies                                                 | Preserve existing reset discovery; workspace removal belongs to PS07, with its separate dependencies.                                                              |
| Encrypted AI outcomes, bindings and original-project recovery                              | Need original AI handoff ownership and durable consumption rules; local capacity release grants no deletion permission.                                            |
| Current project data, managed originals, citations, saved chats and history                | Authoritative project content, outside these exact disposable duplicate locations.                                                                                 |
| Unknown files, links, unsupported/oversized archives, reappearing removals                 | No validated class/identity/complete proof; remain visible in inventory as retained or unclassified.                                                               |

The shared review includes protected-reason explanations. Unknown snapshot entries and unsupported inspection entries can appear as non-selectable rows. Shared incoming/export/migration/reset/AI categories remain in the existing inventory/recovery surfaces rather than being falsely attributed to the current project. No general “Clean all” action exists; unknown bytes are not hidden or subtracted.

## Receipts, retries and discovery

The same `<working root>/retention-actions/<action UUID>.json` registry now accepts a separate strict **v2 local-artifact** record:

`{ version: 2, kind: 'local-artifact', view, selected, context, artifact, target, replacement }`

`artifact` contains the supported class, owning operation ID, snapshot job ID and an exact allowlisted relative filename. `target` contains the derived path, device/inode/size/times, ancestor digest and content hash. `replacement` is PS05's archive proof with actual project/snapshot/head/date. `context` is the owner/mapping digest. The receipt reader reconstructs the path from trusted root/scope/class and rejects mismatches. No project text or credential is copied into a receipt.

Before unlink, the initial receipt records an interrupted/eligible result outside the payload. A small `payload-removals-v1/<SHA256(class:relativePath)>.json` reference under the owning snapshot or file-operation directory records `{ version: 1, actionId }`. The receipt and marker files use atomic temporary writes, file sync and the existing directory-sync helper; new registry/marker directories also have their parent synchronized before unlink. Original `job.json`, `save.json` and `backup.json` are never overwritten by retention.

After persisting, the action rereads its exact receipt/reference, owner metadata and target/replacement identities, including SQLite sidecar absence. One synchronous unlink follows the final checks with no asynchronous gap. **removed** means unlink and supported directory synchronization completed. **changed** means the action did not attempt unlink. **unknown** means unlink or persistence may have happened; it never becomes deletion permission. Final result persistence can itself fail, leaving the initial receipt. Receipts are retained indefinitely within a fixed capacity limit; new removal is refused when that limit is reached.

Status and replay only read the original result. They never run Save, import, export, snapshot creation or another deletion. Replay with a different reviewed artifact is rejected. An absent receipt confirms neither historic non-execution nor removal after receipt loss. The renderer protects one exact request in bounded `collie.local-artifact-action.v1` before dispatch. Unconfirmed outcomes retain Check removal outcome and existing close/project/access protection; malformed preferences disable new removal. No automatic startup replay or deletion occurs. PS05 retains its separate original preference.

The common review UI clears selection on every page and supports Cancel. It has unique labels, controls, pending-action owners and storage keys for previous versions and local artifacts. Result reporting retains the owning IDs. Inventory and existing recovery discovery refresh only when Data is visible. Snapshot discovery already enumerates physically present candidates: intentionally removed candidates are absent rather than synthesized as missing recovery. Remaining/reappearing candidates still appear through the existing guarded inspector. Their exact retention marker prevents another cleanup from deleting a replacement. Receipt/reference files count as operation metadata; payloads still count as recovery/unclassified until actually absent.

Readers predating PS06 do not understand v2 or its marker and cannot infer removal authority. Original snapshot/Save/Backup records retain their prior versions and replay meanings. Older recovery discovery likewise only offers existing local candidates. No portable migration or new import feature is introduced.

## Bounds and practical limits

- Discovery: up to 4,096 entries per listed directory, 16,384 listed entries overall and 4,096 displayed candidate paths. Exceeding limits/unreadable discovery disables eligibility in that review. Paths beyond 4,096 characters remain outside the bounded report.
- Four files per page; at most four destination archives inspected per page, with same-destination reuse within that preview. Each archive and target file is capped at 512 MiB; database files/images at 32 MiB and manifests at 1 MiB. Archive entry/expansion limits remain PS05's. These are resource ceilings, not measured performance claims; content is read more than once.
- Eight in-memory reviews, five-minute expiry; one file per mutation. Full destination/target proof is repeated for confirmation. Unknown or oversize content remains retained.
- The receipt directory retains PS05's shared 1,024-entry cap, receipts are bounded at 128 KiB, and a marker is at most 1 KiB. Marker directories cap at 4,096 entries. Preferences cap at 2,048 characters. No automatic retention expiry or journal purge.

File length is not guaranteed physically reclaimed space. Node supplies no cross-platform atomic conditional unlink by inode; serialized Collie owners and final synchronous checks do not defeat a hostile same-user process racing paths or content. The existing directory-sync helper flushes directories on macOS; Node does not supply the same Windows directory guarantee here. Native I/O, real interruption behavior, large-history costs, accessibility and release acceptance await user observations.
