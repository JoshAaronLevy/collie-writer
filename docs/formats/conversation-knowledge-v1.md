# Project conversation context — AC05

October 8, 2026. SQL/minimum reader **19**, new capture **4**, project-knowledge/selection **1**. This extends AC04 while keeping capture v1–v3 readers/digests, schema 16–18 DDL and direct operation/binding v5 framing unchanged. No provider, credential, SDK, network tool or automatic retry is added.

## Selection and limits

Only explicit Send builds new automatic project material. The worker reads authoritative records under the existing serial project owner; it neither opens nor rebuilds LocalSearch. Opening Context reads saved selections and bounded title lists. Reopening never authorizes inference.

Project context combines the protected current writing, current-chat memory/verbatim suffix, project overview, and one versioned project-knowledge envelope. This chat only and Message only omit the entire project envelope, its pins and project overview. Unsent drafts, other projects and incomplete/local-only attempts are never automatic recall.

- Current Chapter/Section uses its own body and footnotes. Up to 8,000 text units are included; larger automatic items use a query-matching passage with its offset/total in the label. This does not change historical explicit-attachment behavior. Removed ancestors exclude their writing.
- Up to 200 ordered active writing items are considered, with a 1,000,000-unit per-payload and 4,000,000-unit aggregate SQL materialization bound. Full eligible other bodies are included when they fit the writing allocation; otherwise deterministic term matches choose bounded original passages. Direct requested IDs/pins can resolve a target outside that automatic window.
- Project knowledge has at most 24 unique items and a 16,000-unit serialized item budget. Pins and requested identities precede incidental matches. Automatic other writing has up to 7,000 additional units; research has up to 6,000 additional units; other chats use the remaining space. These allocations cannot exceed the total. Long metadata or a bibliography cannot displace the current question and current-chat history.
- Source metadata, active user notes and saved inspection excerpts are distinct item kinds. Excerpts must belong to an active source/attachment and the selected version, and must not have a superseding correction. Metadata is explicitly not evidence that an original was read. Selected source versions can also contribute one passage from already extracted local page text: ranking considers the first 1,000 units of up to 20 pages, and resolution reads the first 4,000 units of up to 32 pages to select up to 1,800 original units. Version ID, page index, text hash and passage offset/total travel in the snapshot. No PDF extraction job or remote URL fetch starts.
- Research and other-chat candidates use up to 200 recent records per category and bounded text for ranking. A chosen chat resolves one relevant completed user/assistant exchange among up to 40 recent completed exchanges. Its captured conversation ID/revision and partial-text offsets remain auditable. It is background discussion, not a transcript role in the current chat or verified evidence. Archived chats are excluded automatically; a deliberate chat pin can include one.
- Broad overview preparation reuses AC04's maximum of one chat and one overview request per Send. For larger material the overview includes bounded opening passages (up to 800 units per covered item, 10,000 total), titles and synopses; originals are kept. Small projects use the raw structural overview and original bodies. Exact snapshot digests invalidate changed coverage. No synopsis-writing chore, background summarizer or unbounded preparation loop is introduced.
- Existing final bounds remain 60,000 context-text and 74,000 serialized prompt/context units, followed by main's existing framed-request admission. Too much indispensable context refuses before inference; no history is silently discarded.

Selection is deterministic and bounded, not exhaustive or semantic recall. The immutable coverage explanation travels with the actual submitted items. Exact IDs, revisions, offsets, total lengths, source/version IDs and pin flags accompany each item; no local filesystem locations or account identifiers are included.

## Pins, exclusions and lifecycle

`conversation_context` stores append-only selection revisions with an explicit current selector per conversation. Each body has up to eight pinned snapshots (16,000 serialized units combined) and 32 exclusions. A project admits up to 1,000 selection revisions without deleting earlier content. The request records its prior revision and exact change; an identical operation retry acknowledges the existing result without another commit. Current selection is never inferred from row order.

Pin/refresh resolves actual project data in the mutation transaction. A pin retains its text/revision until refreshed or removed. Pinning an archived chat is the explicit inclusion action. Exclusions apply to future project selection; they do not erase an already-sent transcript or facts discussed earlier in the current chat. A pinned/excluded current writing item suppresses its automatic live body. Excluded/pinned writing is omitted from the live overview too. Removed, merged or superseded pin targets are omitted from new requests without retargeting the saved snapshot; originals and old captures remain intact.

Selection changes use the existing main command/close barrier, worker edit capability, project transaction/file guard and renderer exact pending-request owner. In-flight work blocks changes. The retained Send checks selection identity after preparation along with AC04's writing/account/model/lifecycle guards. No selection has execution authority.

SQL 18→19 migrates a retained candidate by adding the table; old rows and request digests are unchanged. Manifest admission, copy rekeying, graph checks, full-row retention and exports include selection history and capture provenance. Project IDs are only in table ownership columns, so independent copy rekeys ownership without rewriting snapshot text. AI-linked working copies remain ineligible for removal. Portable readers validate scope targets, selected-version/source links, immutable excerpt bytes, selection lineage/current heads, exact pinned capture membership and the knowledge envelope under the capture digest.

## Source recognition and UI

Completed answers are matched against the whole project's source inventory, not just selected context. Existing DOI/URL normalization is reused; exact source IDs, DOI, URL and ISBN tokens are checked at identifier boundaries. Title matches are suggestions for human review. At most 100 candidate records and 20 displayed canonical matches are returned. Merged records resolve through a bounded replacement chain; trashed records are labeled removed and never restored. No missing match establishes that a reference is new. These local checks require no web capability.

Context → Project material exposes saved pins/exclusions, title search, refresh/unpin/include actions and the last sent coverage. Exact sent snapshots remain in the message menu. Project references offers In Research/Open source or Possible existing source/Review match; captured writing, note, excerpt and chat IDs link only to real scoped records through existing navigation. Discuss in chat opens a new local draft with the saved source pinned; it does not send or overwrite another draft. Actual citation insertion and saving newly discovered references remain AC07.

The React controls retain the existing UI framework, async generation guards, project navigation/draft owners and composition handling. Runtime answer relevance, keyboard/focus, native migration/copy/Save and live provider behavior remain user-owned acceptance.
