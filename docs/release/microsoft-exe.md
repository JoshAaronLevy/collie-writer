# Microsoft Store EXE preparation

October 1, 2026. Local configuration is prepared; native installation, certificate coverage, seller registration, commerce, submission and review remain blocked or unverified. No package was built, installed, uploaded or submitted. This channel is independent of direct-release readiness. See [D8](../decisions/D8-store-channels.md) for the channel decision and effective-policy record.

The selected listing supplies the **exact signed direct-production Windows NSIS x64 installer**. `electron-builder.microsoft.cjs` permits only a native Windows host and the production channel, then exports the direct configuration unchanged. Its NSIS/x64 target is inherited. It does not add Microsoft package identity, MSIX, a Microsoft entitlement origin or a separate updater. A candidate built using this alias is the direct candidate; after signing it once, preserve and reuse those bytes for both download routes. A second build from the same source is not evidence of identical signed bytes.

Both routes use `com.colliewriter.app`, the production local profile/working root, `.collie` association, direct purchase/restore adapter and production update feed. Installing via the listing is intended to upgrade or repair that same installed product. Development and beta remain separate identities. Direct grants remain direct grants; Microsoft account ownership alone does not restore a direct purchase. No entitlement linking with Apple is implemented, and no Microsoft-native purchase claim is made.

Microsoft's [EXE package requirements](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msi/app-package-requirements) require a standalone installer, an immutable versioned HTTPS URL, silent installation, and trusted CA signatures for the installer and every contained Portable Executable. A UAC prompt is allowed. The owner must supply a fresh URL for a changed installer. The Store's EXE route leaves updates with the application; it does not provide the MSIX update mechanism. See Microsoft's [distribution comparison](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/choose-distribution-path).

The current effective [Store policy v7.19](https://learn.microsoft.com/en-us/windows/apps/publish/store-policy-archive/store-policy-7-19) allows third-party commerce for qualifying non-game products; payment-provider, authentication and transaction disclosures still apply. Revisit the effective policy before submission. Collie's existing direct commerce and non-AI value gates must be satisfied before offering paid functionality through this route.

Owner preparation, pending authorization for any publication:

1. On Windows 11 x64, establish the authentic seller, namespace, certificate publisher and owned HTTPS domain described in the [direct installer runbook](direct-installers-and-updates.md). Use the pinned toolchain and lockfile. Set `COLLIE_RELEASE_CHANNEL=production`, `COLLIE_UPDATE_ORIGIN` to that owned HTTPS origin, and `COLLIE_WINDOWS_PUBLISHER` to the actual certificate subject. Keep credentials outside this checkout. There is no supplied certificate or production endpoint to substitute.
2. Produce the electron-vite application output locally, then use `electron-builder --config electron-builder.microsoft.cjs --win nsis --x64 --publish never`. This is an owner build action, not an assistant-run check. The guarded alias selects the existing signed full installer configuration; it does not upload anything. Record this single candidate's version, installer name and owner-obtained hash in the release record. Reuse a previously accepted direct-production EXE instead if it already has that evidence.
3. Establish authentic signature coverage for the installer, uninstaller, application/helper executables, DLLs and native `.node` PE before proceeding. Builder settings and a top-level signature alone do not establish coverage. Any unsigned, incorrectly signed or untrusted PE blocks submission and requires an in-scope signing change plus a new immutable candidate. Current all-PE coverage remains pending owner evidence.
4. Prepare the future versioned HTTPS URL for these retained bytes, such as `https://<owned-origin>/direct/production/collie-writer-production-<version>-x64-setup.exe`; placeholders are not deployed endpoints. Do not use `latest.exe`, overwrite a previously submitted URL, or supply the update metadata URL as the installer URL. Record `EXE`, `x64`, the supported Windows version and installer parameter `/S` for a later Partner Center submission. Microsoft describes these fields in [uploading EXE packages](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msi/upload-app-packages). Record only actually observed exit-code meanings.
5. Keep listing assets, privacy/support URLs, seller identity, purchase disclosures and manual results together for later review. Registration, hosting/upload, public listing and submission each remain unperformed and require separate authorization. A source configuration is not Store approval.

As a user, after an authentic candidate is available:

1. On a disposable clean Windows 11 x64 installation, run the retained installer with `/S`; installation should finish without installer pages or a download phase, with only any necessary UAC prompt. Record unexpected windows, prompts or failures instead of marking this accepted.
2. Open Collie Writer and save a disposable project; editing and saving should work through the normal offline flow. Close it, install the same production product through the other authorized distribution route, and reopen it; the same local work should remain available without a second production identity or a reset.
3. Use Help → Check for updates after an approved newer candidate is available; Collie should use its existing production update flow and request permission before download and restart. A Microsoft Store-managed update or Microsoft purchase-restore screen is not part of this EXE route.
4. After authentic direct commerce is configured, restore the same direct purchase through either installation route; the shared capability policy should apply the same rights, while reading, export, backup and recovery remain available after entitlement changes. Keep real refund, renewal, offline access and lifetime observations pending until performed.
5. With only disposable local work and separately saved backups, uninstall and reinstall the same product; app removal should retain the production profile and working root unless the user or OS separately deletes them. Reopen a chosen `.collie` backup independently, and record the actual recovery outcome. Do not use unsaved personal work for this scenario.
