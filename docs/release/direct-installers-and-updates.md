# Direct installer and update owner runbook

Stage 21 local release preparation, October 1, 2026. All building, signing, artifact inspection, installation, update observation and publication are owner actions. This document does not assert any of them occurred. Never place signing keys, Apple credentials, Windows certificate files, merchant secrets or a draft manuscript in the repository or a support preview.

Before preparing either channel, confirm the legal seller/publisher identity, control of the chosen application namespace and HTTPS feed domain, `com.colliewriter.app` registration/availability, certificate subject/Team ID, and a clean release machine with the pinned Node/npm and lockfile dependencies. Record the actual issuer, host, certificate subject, OS and architecture privately. Resolve any namespace conflict *before* distributing an identity; changing it later breaks Windows upgrade and separates local data. Keep production, beta and development app IDs and feeds distinct. Stage 20 merchant/value gates remain independent and still block a paid launch.

For a **macOS direct candidate**, use the verified Developer ID Application identity in `COLLIE_MAC_IDENTITY`, approved Apple notarization credentials recognized by electron-builder v26, `COLLIE_RELEASE_CHANNEL=production` or `beta`, and `COLLIE_UPDATE_ORIGIN` set to an owned HTTPS origin with no path. Use a clean lockfile installation, produce the electron-vite application output, and package with `electron-builder --config electron-builder.direct.cjs --mac --publish never`. This requests arm64/x64 DMG and ZIP, code signing and notarization. An Apple signing/notarization/stapling failure is a blocked artifact. The beta channel requires changing `package.json` to a `-beta.N` version before building; keep a separate recorded version lineage. Do not upload any artifact just because packaging returned.

For a **Windows direct candidate**, build natively on Windows 11 x64 with a trusted code-signing certificate, set the exact certificate subject in `COLLIE_WINDOWS_PUBLISHER`, the same verified channel/origin choices, produce the electron-vite output and package with `electron-builder --config electron-builder.direct.cjs --win --publish never`. The configuration requires code signing and creates a full per-machine NSIS installer, so an administrator prompt is expected. The publisher name in the installed `app-update.yml` must match the package metadata and actual Authenticode certificate; otherwise update checks remain disabled or downloads are rejected. Do not substitute an unsigned `build:win` development output. Signing alone does not establish SmartScreen reputation.

For each candidate, the owner should record installer name, version, channel, SHA-256, OS/architecture, Apple Team ID and notarization/stapling status or Windows Authenticode publisher/chain, and the exact bundled `.node` architecture. Inspect both app and installer signatures and the ZIP/DMG/NSIS contents, bundled resource and dependency/license notices, and absence of secrets or content-bearing diagnostics. Exercise a clean-machine install and reopen with disposable project copies. A compiled artifact, source review, unsigned package or cross-compilation is not native proof.

Stage 22's [Microsoft Store EXE route](microsoft-exe.md) reuses the exact retained Windows production installer, including its profile, commerce and updater. Do not create or re-sign a second Store variant. Windows signing now explicitly includes `.dll` and `.node` alongside builder's default EXE signing; the owner still needs actual coverage evidence for every shipped PE. MAS and MSIX are not direct package targets and their runtimes are refused; see [D8](../decisions/D8-store-channels.md). The [Stage 23 manifest](release-candidate-manifest.json) has deliberately empty candidate/artifact/approval fields until authentic outcomes are supplied.

If a signing key or notarization credential is exposed, stop release and update publication, revoke/rotate through the issuing authority, and prepare a deliberately trusted transition before resuming. Never log or commit the secret. A Windows publisher-subject change needs a reviewed bridge release; this updater currently pins one publisher name and will reject another.

The generic feed is private/unpublished until a separate publication authorization. If authorized later, distribute the generated `latest.yml` / `latest-mac.yml` (or beta channel filenames) and their exact signed full artifacts under only `https://<owned-origin>/direct/<channel>/`. Keep immutable versioned installers and pre-migration recovery copies; switch a feed to a new version only after independent user observations. No redirect to another host/channel, web installer, staged rollout percentage, dynamic artifact rewrite or production/beta mixing is allowed. An update requires a newer signed version; the application checks only when Help → Check for updates is chosen. It asks before downloading and before restart. If the owner later wants periodic checks or staged rollouts, that is a separate privacy/security decision.

For a bad update, stop serving it and retain the prior signed installer, migration copy and user-selected backups. Do not point the feed at a lower version: the updater rejects downgrade. A user can reinstall a reviewed prior installer to repair binaries, but must preserve the current workspace and use a compatible pre-migration copy if the old app cannot read the new format. Never delete or treat `working/`, `reset-recovery/`, file-operation candidates, selected `.collie` files or retained previous copies as updater cache. A failed download/interrupted install should leave the prior app and data available; document the observed result before declaring rollback successful.

Windows NSIS is configured with `deleteAppDataOnUninstall: false`; its uninstaller should leave the channel's app profile and local working root. macOS Trash removal of the app bundle should likewise leave those separate locations. A user who deletes the profile/working root, accepts an OS “remove associated data” option, or loses the disk may lose unsaved recovery; a selected `.collie` file and independently chosen backup are outside the app install but remain subject to that location's OS/cloud behavior. Reinstalling the same channel should reuse its local root; switching channels starts an independent root and does not silently import recovery. Confirm each behavior on disposable copies before saying it is proven.

Pending release gates: actual Apple/Windows credentials, namespace/domain verification, native rendering review of the [approved artwork](../validation/app-branding.md), native signatures/notarization, clean-machine macOS arm64/x64 and Windows 11 x64 results, real update/partial-download/interruption outcomes, file association and migration/recovery observations, security inspection of new dependency tree/artifacts, and full Stage 20 commerce/value completion before paid release. No public publishing or live purchase was authorized in Stage 21.
